## 定義(本流)

**大きな付箋** は [Kozaneba](../entities/Kozaneba.md) の機能で、こざね / group の **`item.scale` 属性を増加** させることで通常より大きく描画される付箋。**ズームアウトしても読める** ことで [なめらかな畳まれ](なめらかな畳まれ.md) の効果に対する **能動的な対抗手段** として nishio が日常的に使っている。

## 出典

[pKozaneba2025-08-26~27](../../raw/scrapbox_kozaneba/2025-08-26__pKozaneba2025-08-26~27.md) より:

> ズームアウトすると読みにくくなることを「なめらかな畳まれ」に使っている。**「大きな付箋」を使っている、ズームアウトしても読める付箋として**。

## 本流の実装

`work/kozaneba/` を読んで確認した実装:

- **データモデル**: [`RTKozaneItem`](../../work/kozaneba/src/Global/TKozaneItem.ts) と [`RTGroupItem`](../../work/kozaneba/src/Global/TGroupItem.ts) の両方が `scale: Number` 属性を持つ。base = 1
- **UI**: [`BigSmallMenuItem.tsx`](../../work/kozaneba/src/Menu/BigSmallMenuItem.tsx) — 選択した こざね / group に対して **big**(`scale++`)、**twice**(`scale *= 2`)、**small**(`scale--`)、**half**(`scale = floor(scale / 2)`)の 4 操作。`scale >= 2` で `small` 表示、`scale >= 4` で `half` 表示
- **描画**: [`useAdjustFontsizeStyle.tsx`](../../work/kozaneba/src/Kozane/useAdjustFontsizeStyle.tsx) で box の `width = KOZANE_WIDTH * scale`、`height = KOZANE_HEIGHT * scale`、フォントは `adjustFontSize(text) * scale * shrink_on_print`。**箱とフォントが同じ scale で線形に拡大**
- **オフセット計算**: scale 拡大時も中心が同じ位置に保たれるよう、`offset.x - (scale * KOZANE_WIDTH) / 2` で位置補正

つまり「大きな付箋」は **新規 item 型ではなく既存 こざね / group の `scale` 属性の増加** で実現される。専用の「見出しこざね」型はない([関係を第一級にする](../themes/関係を第一級にする.md) で議論される first-class でない事例)。

## semantic zoom の人力代替

ズームレベルに応じて何が読めるかが変わる:

- **ズームイン**: 全ての付箋が読める
- **ズームアウト**: 通常のこざねは読めなくなる、**大きな付箋だけが読める**

つまり 大きな付箋 はユーザが自分で「これは上位の見出し / 代表的なもの」と決めて、`BigSmallMenuItem` の操作で **semantic zoom の上位層を作る** 手段。

これは [畳むUIの再設計](../themes/畳むUIの再設計.md) で挙げた **Heptabase 型 inverse-zoom title**(group 表札がズームアウトで大きくなる)の **人力先行版** に位置付けられる。AI 自動表札([Canvas 1 万件デモの拡張](../themes/Canvas_1万件デモの拡張.md))を入れるなら **大きな付箋 = 自動生成される frame 表札の手動版** という相同関係で読める。

## なぜ「KJ法 ではなく こざね法」になっているか

[pKozaneba2025-08-26~27](../../raw/scrapbox_kozaneba/2025-08-26__pKozaneba2025-08-26~27.md):

> KJ法 ではなく [こざね法] だねこれ。グループ化はしているが、まとめて動かしやすくするためだけに使われている。KJ法 的な「表札をつけて束ねる」をやってない。

[KJ法](KJ法.md) の [表札をつけて束ねる](表札をつけて束ねる.md) を Kozaneba が UI 上で(意識的にか無意識にか)避けた結果、その代替として:

- **大きな付箋** で見出し的な役割を担わせる
- **[なめらかな畳まれ](なめらかな畳まれ.md)** で表示密度を切替

の 2 つで「束ねた効果」を模倣している。この補完関係を理解しないと「KJ法 機能の不足」と「実際の使い方」が乖離して見える([活用されなかった機能](../themes/活用されなかった機能.md))。

## 同名異物: プロトタイプの「大きな付箋」と区別

[Canvas 1 万件プロトタイプ](../themes/Canvas_1万件デモの拡張.md)(`work/canvas_kozaneba_prototype/`)のコードにも「大きな付箋」という用語が頻出するが、**指すものが違う**:

| | 本流(このページ) | プロトタイプ |
|---|---|---|
| 単位 | 個別 こざね / group | cluster 全体 |
| 機構 | `item.scale` 増加 | `clusterRender = 'sticky'`(2025-08-29 default 化、commit `d8f1053`) |
| 操作 | ユーザがメニューで big/twice/small/half | アルゴが自動生成、UI モード切替のみ |
| 思想 | ユーザが意思決定して上位構造を作る | アルゴが密集を検出して上位構造化 |

両者は **「ズームアウトでも読める単位を作る」思想で一致** しているが、実装と起点が違う。Wiki 内で「大きな付箋」と書くときはどちらを指しているか明示する。

## ユーザ拡張機能としての性格

専用の「見出しこざね」型ではなく、汎用 [こざね](こざね.md) の `scale` 属性を増やして使う点が Kozaneba らしい:**ユーザが工夫して使うことで意味が生まれる**(cf. [ドッグフーディング](ドッグフーディング.md))。新しい型を増やさずに既存型の属性で対応する設計判断は [活用されなかった機能](../themes/活用されなかった機能.md) の「先回りした一般化を避ける」とも整合的。
