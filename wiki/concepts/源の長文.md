## 定義

**源の長文** は、[こざね](こざね.md)(短いラベル / 断片)が **そこから生えてくる** ところの、長めのメモ・経験・原文・会話。[関係場](関係場.md) の Pipeline でいう **Situation** に相当する。

2026-05-16 のセッションでの nishio の観察:

> Kozaneba のこざねは Scrapbox のページタイトルに相当するもので、現状のこざねは「ページ本文」に相当するものを持っていないように思う。一方で Scrapbox の「ページタイトルとページ本文が1対1対応」もおかしくて、1つの長文から N 個の短文(=タイトル/こざね)が生えていると思う。

つまり「源の長文 1 つ → こざね N 個」というカーディナリティが実体に近く、現状の Kozaneba にも Scrapbox にもこの構造が明示的に表現されていない。

## Pipeline 上の位置と既存ツールの欠落

[関係場](関係場.md) の Pipeline と既存ツールの対応:

| Pipeline | Scrapbox の現状 | Kozaneba の現状 |
|---|---|---|
| Situation | ページ本文 | **欠落** |
| Aspect | ページタイトル(本文と 1:1 で固定) | こざね |
| Relation Field | リンクが弱く担う | 欠落(線で直接 Projection) |
| Projection | リンクグラフ | キャンバス配置 |

- **Kozaneba** は Aspect(こざね)と Projection(キャンバス配置)を持つが、Situation を持たない
- **Scrapbox** は Situation(本文)と Aspect(タイトル)を持つが、1:1 でカーディナリティが間違っている
- 実体: 1 長文 → N こざね

## 「こざね」の定義のズレが効いてくる

[こざね](こざね.md) で整理しているように、語源の梅棹忠夫の「こざね」と Kozaneba の「こざね」は Pipeline 上の位置が違う:

```
梅棹こざね:    断片 + 断片 + 断片 → ホッチキスで綴じた1つの「思想の定着」   ≒ Relation Field
Kozaneba こざね: 1つのテキスト断片                                          ≒ Aspect
```

両者は名前が同じだが扱う層が異なる。そして **共通して Situation(源の長文)を明示的に持たない**。これは梅棹もデジタル化された Kozaneba も両方共通する盲点。

## Scrapbox の暗黙ワークフロー: 半分だけ実装されている「1 長文 → N タイトル」

Scrapbox の実運用では:

- 長文(メモ・日記・読書ノート)を書く
- その中で重要な部分を bracket で囲んでタイトル化する
- そのタイトルが別ページとして独立する
- 結果として「1 長文 → N タイトル」が生まれる

ただし問題:

- 分割操作は完全に手動
- 分割後、元の長文との接続は「ページ間リンク」に圧縮されて薄くなる
- 後で「このタイトルはどの長文の、どの部分から生えたのか」を辿るのが困難
- 元の長文側にも「ここからこのタイトルが生えた」というマーカーが残らない

[Scrapboxこざね](Scrapboxこざね.md) は逆方向(タイトル側から長文側への参照を保つ)を部分的に実装しているが、「自分の長文から自分のこざねを生やす内側のループ」は弱い。

## 外部の類似物

| ツール / 概念 | 関連する設計 |
|---|---|
| Andy Matuschak の evergreen notes | 1 atomic note ≒ 1 こざね、だが各 note 自体が body を持つ。document literature notes(長文相当)から evergreen notes を「蒸留する」明示プロセスを推奨 |
| Roam Research / Logseq の block model | block transclusion で「1 long passage の中の N 個の block が他所から参照される」を実装。長文と短文の関係をデータ構造で保持 |
| Outliner 系 | indent で「親 long → 子 short」を表現するが、子は親の文脈に縛られすぎる(独立した Aspect として動けない) |
| Tools for Thought 文化 | literature note → evergreen note → MOC(map of content)という蒸留のレイヤ分割 |

これらと比べて、Kozaneba のこざねは **「源の長文への参照」というフィールドを構造的に持っていない**。データモデルの欠落と読める。

## 設計含意: データモデル案

```
こざね R {
  text: "...",                  // 現状あるもの
  source_situation: {            // 新規: 源の長文への参照
    text: 長文 / メモ全体,
    anchor: 長文内の位置(段落 / 文 / 範囲),
  },
  sibling_aspects: [R1, R2, ...] // 同じ source_situation から生えた他のこざね
}
```

これがあると:

- **1 長文 → N こざね** の関係が保持される
- 「このこざねはどの長文の何段落目から生えた?」が辿れる
- 同じ Situation から生えた こざね 同士は **関係場候補** のヒントになる(LLM が拾える)
- [思い出し効果](思い出し効果.md) が長文側にも適用できる(タイトル/こざねを見たら本文が想起される、の Kozaneba 版)
- [Clean Relation Elicitation](../themes/Clean_Relation_Elicitation.md) の Situation Pad が、こざねごとに紐づいた形で存在することになる

## Kozaneba の現状の「こざね」が持っているもの

参考までに、現状の Kozaneba のこざねが持つフィールド:

- text(短いテキスト)
- 位置(キャンバス上の x, y)
- サイズ(大きさで重要度表現)
- グループ(畳まれていれば親グループ)
- 種類([Scrapboxこざね](Scrapboxこざね.md) / [Gyazoこざね](こざね.md) / 通常)

「源の長文」相当のものは、[Scrapboxこざね](Scrapboxこざね.md) で URL を経由した間接参照としてだけ存在し、自前のテキストフィールドとしては無い。

[work/kozaneba コード構造調査](../sources/kozaneba-code-architecture.md) で確認した実コード(`RTKozaneItem`)でも、`text / position / scale / custom.{ style?, url? }` 以上のフィールドは無く、**`source_situation` 系のフィールドはどの Item type にも存在しない**。Item の Union は `kozane / group / scrapbox / gyazo` の 4 種で、長文を保持する型は無い。Plan B での「最小改造」候補としては、(a) `RTKozaneItem` に optional な `source_situation: { text, anchor }` を追加、(b) `RTSituationItem` という新 Item type を加えて `items[]` 経由でこざねと繋ぐ、(c) Firestore に別 collection を切る、の 3 案が考えられる。

## Plan B と Plan A の共通基盤としての位置

2026-05-16 の [3 Plan 議論](../themes/3plan議論.md) で、現 Kozaneba 改造(Plan B)と新規サービス(Plan A)の両方で「源の長文」データモデル拡張が **共通基盤** として必要と整理された:

- **Plan B**: 300 件の文章から知識獲得する作業を加速するため、各こざねが「どの長文の何段落目から生えたか」を保持する必要がある。**先に着手する基盤実装**として位置づけ
- **Plan A**: ConnectingDots の Dots(検証可能な事実、出典あり)層に対応する基盤として必須([sources/llm-wiki-cross-reference](../sources/llm-wiki-cross-reference.md))

Plan B 期間で本データモデルを実装すること自体が、Plan A の要求発見・基盤整備を兼ねる。「Plan A 要求発見のために Plan B 期間で記録すべき 5 項目」のうち **5. Situation から複数こざねが生まれた経路** がここで検証される。

## 既存議論との接続

この観察は [断片中心から関係中心へ](../themes/断片中心から関係中心へ.md) の重心移動論と並走するが、論点が違う:

- 「断片中心 → 関係中心」: 断片の **横の関係性** を扱うべき
- 「源の長文の欠落」: 断片の **縦の由来**(=どこから生えたか)を扱うべき

両方とも「断片偏重」の症状だが、横の問題と縦の問題で別レイヤ。

## 開いた問い

- 「源の長文」は誰のものか? 自分のメモか、引用元の他人の文章か、会話ログか? 種類によって扱いが変わるか
- 既存の Scrapbox 本文を「源の長文」として Kozaneba に取り込む既存パイプライン([Scrapboxこざね](Scrapboxこざね.md))との関係
- LLM 時代には「長文を書く → こざねを生やす」を AI が補助できる(cf. [Clean Relation Elicitation](../themes/Clean_Relation_Elicitation.md) の Lift 操作)
- [Plurality](Plurality.md) / [広聴AI](広聴AI.md) の文脈では、源の長文は「意見の集合 / トランスクリプト」、こざねは「クラスタの代表ラベル」になる。スケールが違うだけで構造は同型かもしれない
- [Kozaneba読書](Kozaneba読書.md) のような用途では、源の長文 = 読んでいる書籍。これは既に自然にそうなっているが、データモデル上は紐付いていない
