## 定義

**物理演算** は、[Kozaneba](../entities/Kozaneba.md) における **付箋を「バネ・反発・引力」のような物理モデルで自動配置する** 機能。2021-09 にグラフ可視化(ソースコードのインポート関係など)のデモを念頭に実装された。

[Kozaneba開発日記2021-09-09](../../raw/scrapbox_kozaneba/2021-09-08__Kozaneba開発日記2021-09-09.md):

> 物理演算による自動整形機能が追加された。
> ユーザスクリプトで物理演算ボタンをつける。

## 設計上の葛藤

nishio 自身が当初から「**入れていいのか?**」を悩んでいる。[Kozaneba開発日記2021-09-06](../../raw/scrapbox_kozaneba/2021-09-06__Kozaneba開発日記2021-09-06.md):

> Kozaneba に物理演算入れたくなっちゃうけど **物理的な配置が知的生産物であるところに機械的に物理演算掛けちゃったらダメな気がする** しなぁ。

> むしろあれか、物理演算をオンにしたタイミングで近接していたものは「人間が近接によって表現した関係である」として近接関係が維持されるような物理演算にすればいいのか。

> でもそれを言い出したら「少し離して置いてある」も「関係はあるがすぐそばに貼り付けるほどではない」という表明なわけで…

これは Kozaneba の根源的な設計判断「**配置は人間の知的生産物だから機械が動かしてはいけない**」と、グラフ可視化のような実用ニーズの折衝が生む葛藤。

## 実装したが期待ほどではなかった

[Kozaneba開発日記2021-09-09](../../raw/scrapbox_kozaneba/2021-09-08__Kozaneba開発日記2021-09-09.md):

> 物理演算を入れたけど現状ではあんまり面白くないな。
> 矢印が集まりまくってる頂点を削除したり、ディレクトリ階層をグループで表現したりする手はある。

[2021-09-10](../../raw/scrapbox_kozaneba/2021-09-10__2021-09-10.md):

> 物理演算のステップ自体は 200ms くらいなので、単純に描画が重い。まあ、この用途はメインの目的ではないので **負荷テストみたいなものと解釈しておこう**。

つまり物理演算は **メインの目的ではない** という位置づけになった。グラフ可視化機能としては [毛玉問題](毛玉問題.md) を解消する根本的解決にはならなかった。

## 現コードでの実装(2026-05 時点)

[work/kozaneba コード構造調査](../sources/kozaneba-code-architecture.md) で確認した実装は、シンプルな 3 法則の加算合成:

| 法則 | 概要 |
|---|---|
| `ItemRepulse` | 全 Item ペア間距離 `n < RADIUS = √(KOZANE_WIDTH² + KOZANE_HEIGHT²)` のとき `(RADIUS - n)/2` で反発 |
| `LineSpring` | 各 line annotation について、参加項の重心点に向けて、自然長 `NL = KOZANE_WIDTH` を超える項を引き寄せ |
| `pin` | ピン留めされた Item を固定 |

更新は `AdaDelta` か `GradientDecent` クラスで勾配を消化し、`TERMINAL_VELOCITY = 200` で発散を抑える。

**設計上の含意:** `ItemRepulse` は全ペア走査の **O(N²)**。2021-09 開発日記の「ステップ自体は 200ms くらい」の原因はここで、大規模化([Canvas移行の検討](../themes/Canvas移行の検討.md))と相性が悪い。物理演算が「メインの目的ではない」と位置づけられたことと、その実装がペア走査の素朴アルゴリズムに留まっていることは整合的(本気でやるなら quadtree / Barnes-Hut にする必要があるが、そのコストを払う動機が無かった)。

## 2026-06: データ層と空間 index を共有する道

[データモデル刷新の選択肢](../themes/データモデル刷新の選択肢.md) で SQLite WASM(SQLocal + R-tree)系を検討した結果、**データ層に空間 index を入れる選択肢は物理演算の O(N²) も同時に縮退できる** ことが明らかになった:

- R-tree(rbush 等)を SQLite 側に持ち、「視界内 + 近接ペア」だけを物理計算
- これは quadtree / Barnes-Hut 化と等価な効果を、データ層と物理層が **同じ index を共有する** 形で得る

つまり Loro 単独や Yjs 単独ではなく、**Loro + SQLite WASM(空間 index)+ CAS blob** の三層構成が、データサイズ / 物理スケーリング / 長文 の 3 問題を同時に解く統合解になりうる。Plan A 寄りの全面書き直しなら直接そこを狙える。

[畳むUIの再設計](../themes/畳むUIの再設計.md) の group → frame 化(自前 bounding rect)とも噛み合う: 畳まれた group は **物理的に 1 点質量** として近似でき、O(N²) の N が実効的に減る。
