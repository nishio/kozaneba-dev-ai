## 定義

**辺ラベル**(エッジラベル)は、[線を引く機能](線を引く機能.md) で引かれた線の上に貼るテキストラベル。「A → B」だけでなく「A → B(関係: 含意)」のように関係の種類を表現するために必要。

## 三項関係としての位置付け

[pKozaneba](../../raw/scrapbox_kozaneba/2021-08-10__pKozaneba.md) の項目リスト:

> [辺ラベルは三項関係]

辺ラベルがあるということは「(始点, 関係, 終点)」という三項関係を扱うこと。

## 2025 年の実装の試み

[pKozaneba2025-09-11](../../raw/scrapbox_kozaneba/2025-09-11__pKozaneba2025-09-11.md): [Devin](../entities/Devin.md) が辺ラベル機能を実装。「線のデータ構造にラベルフィールド追加」「ビューでの表示追加」「作成時にラベル入力ダイアログ追加」を全部やってくれた。ただし、ダイアログが「明らかにウザい」ので作成時 UI のみ不採用。

選択肢:

- A: 「ラベル付き線」「ラベル付き矢印」の追加メニューを別に作る
- B: 線をクリックして「ラベルをつける」メニューを出す

[Kozanebaにエッジラベルをつけると良いのでは](../../raw/scrapbox_kozaneba/2025-09-14__Kozanebaにエッジラベルをつけると良いのでは.md):

> エッジにイベントリスナがついてない... これは厄介。ビューとしてエッジラベルを出すことはできるし、エッジラベルのあるグラフをインポートすることもできるけど、通常の UI でエッジを対象としたアクションができないのでラベル追加もできない...

→ エッジへのイベントリスナ追加が必要。

## なぜ今必要か

[いどばた/Keichobot→概念マップ→Kozaneba/Miro](../../raw/scrapbox_kozaneba/2025-11-14__いどばた_Keichobot→概念マップ→Kozaneba_Miro.md):

> [Keichobot](../entities/Keichobot.md) 的コーチングは **概念とその関係** を抽出するので、概念マップ研究と関連深い。概念マップの研究を進める上でグラフを単に可視化するだけではなく操作したい、これは今まで西尾は Kozaneba でやってきたこと。ただ、辺ラベルの機能がないのが今のニーズに不足。

→ Kozaneba に辺ラベルをつけるか、Miro でやるかの選択肢が出ている。

## N項関係 → 関係場への発展(2026-05)

辺ラベル(三項関係)は [N項関係](N項関係.md)、さらに [関係場](関係場.md) への発展の出発点でもある。[raw/関係UI議論_GPT.md](../../raw/関係UI議論_GPT.md) Round 2 で論じられたように、辺(エッジ)を「単なる線」として扱うのではなく **第一級オブジェクト**(type / participants / anchors / polarity / modality / temporal scope / provenance / confidence / visibility / lifecycle を持つ)として設計する流れの最低限の入口が辺ラベル。

既存系譜(Open Hypermedia / Wikidata の qualifier / RDF 1.2 triple term / W3C N-ary Relations)はすべて、辺ラベルよりさらにリッチな関係表現を扱う仕組み。詳細は [関係を第一級にする](../themes/関係を第一級にする.md)。

## 2026-05: コード上はデータモデルが既に完成している

[work/kozaneba コード構造調査](../sources/kozaneba-code-architecture.md) で確認したところ、`RTLineAnnot` には既に `label: String.optional()` フィールドが入っている。2025-09 の [Devin](../entities/Devin.md) 実装で「線のデータ構造にラベルフィールド追加」「ビューでの表示追加」までは Merge 済みで、PR #36 で「作成時ダイアログのみ撤去(うざい)」が確定した状態が現在の main([git history 2025](../sources/kozaneba-git-history-2025.md))。

つまり残っている課題は:

1. **既存の line annotation を選択する経路** — `AnnotationLayer.tsx` が SVG レイヤ全体に `pointerEvents: "none"` を指定しているため、エッジクリックが基本的に不可。個別 `<line>` は `custom.is_clickable: true` のときだけ反応する設計で、既存データはほぼ全部 false 相当
2. **ラベル入力 UI** — 「線を引いた瞬間に必須入力」を外したので、別経路(線クリック → ラベル編集メニュー / Selection からの一括ラベル付け / LLM 候補からの選択)が必要
3. **表示時のラベル配置** — 線の中点付近に置く既定実装はあるが、複数線が交差する場面での読みやすさは未確認

「ラベル機能が無い」という Scrapbox メモ群はもう古い。**いまは「ラベル `field` はあるが、それを編集する UX 動線が無い」状態**と書き換えた方が正確。

## 2026-06: 外部ツール文献サーベイの含意

[線UIサーベイ 2026](../themes/線UIサーベイ_2026.md) で 16 ツールの辺ラベル UI を比較した結果、三大パターンが浮かんだ:

1. **描いた瞬間 inline caret**(Whimsical / FigJam):線の中点に caret 出現、書けば書く、書かなければスキップ。**modal dialog ではない**ので押し付けにならない
2. **後から double-click**(Miro / tldraw / Obsidian Canvas / draw.io):デフォルト無ラベル、編集は意図的
3. **構造的・限定語彙**(Kinopio の `connection-type` / Tana の field):ラベル = 型、ユーザが育てる constrained vocabulary。色とラベルが連動

2025-09 の Devin 実装が失敗したのは **「描いた瞬間 modal dialog」というアンチパターン** を踏んだから。「描いた瞬間 inline caret」または「後から double-click」に切り替えれば、思考の流れを止めずに済む。

Kinopio 型の **connection-type**(`label: string?` を `label + type_id` に拡張)は、関係名を「supports / contradicts / is-example-of」のようなユーザ語彙として育てる方向で、Kozaneba の中核と相性が良い。

## エッジラベルダイアログが「ウザい」問題への別解

2025 年の Devin 実装で「線を引くたびにラベル入力ダイアログ」が不採用になった理由は、ラベルを **強制入力** にしたから。[Clean Relation Elicitation](../themes/Clean_Relation_Elicitation.md) のアプローチでは、ラベルを「ユーザ語(原文から拾う)」と「システム候補語(LLM 提案)」に分け、後者は `[どれも違う]` `[まだ言えない]` を許す。これによりラベル付けが思考の流れを止めない。
