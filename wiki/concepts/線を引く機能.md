## 定義

[Kozaneba](../entities/Kozaneba.md) の機能の一つ。**離れたものの間の関係を、空間的近接によらず線で明示する**。本家の[こざね法](こざね法.md)では行わず、[KJ法](KJ法.md)では空間配置が完了したあとに行われていた。電子化したことで「動かす前から線を引ける」ようになった点が革新。

## なぜ必要不可欠か

[Kozaneba:体験過程と意味の創造](../../raw/scrapbox_kozaneba/2021-12-08__Kozaneba_体験過程と意味の創造.md):

> 線がなければ付箋は近接という関係しか持てない。付箋は一つの場所しか持てないので、明確な境界はないとは言え階層的分類の要素が出てくる。コウモリ問題の「どちらに入れよう」に相当する「どちらに置こう」が発生する。
>
> これは、まだ構造が全くないものに対して構造を見出すときには「どっちかにしか置けないからエイヤで置く」というドライブフォースになる。しかし、この制約は「書籍を読んでそれを理解する」のようなときに邪魔になる。なぜなら書籍は既に著者によって構造化されているから。

つまり書籍を読んで理解する(=既に[既存の構造](既存の構造の破壊.md)がある)用途で線は不可欠。

## 推敲(チュートリアル文章の書き直し)

[Kozaneba:推敲:線を引く機能](../../raw/scrapbox_kozaneba/2022-03-08__Kozaneba_推敲_線を引く機能.md) は、線を引く機能の解説文を nishio が[推敲](推敲.md)した記録。葛藤:

> 線を引く機能は有益だが、まだこれらの手法に慣れていない人にも有益なのかよくわからない。選択肢が増えて悩むことが増し、実益にたどり着くまでの道が長くなってしまわないか心配しているのでチュートリアルに入れるかどうかためらっている。

これは「ユーザ体験設計のジレンマ」の典型例として保存に値する。

## コード上の線種(2026-05)

[work/kozaneba コード構造調査](../sources/kozaneba-code-architecture.md) で確認したところ、Annotation 種別は `line` のみで、見た目の差は `heads: ("none" | "arrow")[]` と `is_doubled: Boolean` の組合せで全て表現される:

| ユーザから見た線種 | データ表現 |
|---|---|
| 線(無向) | `heads: ["none", "none"]`, `is_doubled: false` |
| 矢印(片方向) | `heads: ["none", "arrow"]`, `is_doubled: false` |
| 双方向矢印 | `heads: ["arrow", "arrow"]`, `is_doubled: false` |
| 二重線 | `is_doubled: true` |
| 削除モード | データには残さない、描いた線で交差した既存線を削除する操作 |

`heads` が `items` と同じ長さの配列であることは「**`items.length > 2` の関係でも各端点ごとに矢印頭を独立指定できる**」という設計余地を示す([N項関係](N項関係.md))。これは現 UI では使われていない潜在能力。

「エッジにイベントリスナが付いていない」問題のコード由来も判明: [`AnnotationLayer.tsx`](../../work/kozaneba/src/Canvas/Annotation/AnnotationLayer.tsx) は SVG 全体に `pointerEvents: "none"` を付けて背景にイベントを通している。個別の `<line>` は `custom.is_clickable: true` のときだけ `pointerEvents: "auto"` を復活する設計で、既存データはほぼ false 相当のためクリック反応しない。

### エッジに反応を付けない設計意図(フォーラム解説)

公開フォーラムの [Scrapbox Integration](../../raw/kozaneba-forum/Scrapbox_Integration.md) (2022-05-26) で nishio は明示的に書いている:

> 以前、線に当たり判定をつけて設定メニューが出るようにしようとしたことがあって、これも「こざねを動かすこと」の妨げになったのでやめました
>
> I once tried to make the setting menu appear by putting a hit detection on arrow annotations, but this also interfered with "moving the kozane", so I stopped!

「こざねを動かす」が最頻出の操作なので、`AnnotationLayer` の `pointerEvents: "none"` は **意図された設計**であり、辺ラベル / 辺メニューの実装はこの根本制約と衝突する。「辺をクリックする」と「こざねをドラッグする」をどう両立するかは未解決問題のまま。

## 2022-2023 の UX 改修(Release Notes より)

[Release Notes 2021-2025 要約](../sources/release-notes-2021-2025.md) で確認した、線関連の UX 改修の集中期:

- **2022-01-25**: `Leave from lines` menu (線連想からの離脱)
- **2022-05-26**: 矢印 head と body を一緒に半透明化、**長さに応じて opacity が滑らかに変化**、分岐・二重線も同様化。短い線が長い線で埋もれる問題への対処
- **2023-01-26**: Context menu からの線作成 UX (`線を作る → 対象クリック → 確定` の 3 step、空クリックで cancel、line 削除も同 UX)。`Enter` で AddKozane Dialog。`kozaneba.constants.to_adjust_opacity_of_lines_by_length` を公開 API として露出
- **2023-02-06**: Line drawing mode 中の **drag は target の selection 扱い** (以前は drag 中だと「click による線描画」が trigger されず無反応に見える問題)。`Draw lines` menu の調整 (1 → N の親→子線が引きやすく)。**左右判定を bounding box の重心 → midpoint に変更** (要素数が多いと重心が直感に反するため)

`to_adjust_opacity_of_lines_by_length` を constants で ON/OFF できるようにした 2023-01-26 の判断は、**「思考整理 stationery」 vs 「説明 diagram」** という二つの使用文脈への自覚を反映している:

> Kozaneba sets higher transparency for longer lines. This is an expression of "related but the relation is not important" because they are placed far apart. [...] However there is a use case where Kozaneba is used to create a diagram to communicate something to others [...] In such cases, it is sometimes better not to have different line colors. So I made it possible to switch between them. — default: true

default を stationery 側に倒した事実は「Kozaneba は説明用 diagram ツールではない」設計判断の継続を示す。

## 外部ユーザの「線」UX 報告

公開フォーラム [解決:Add Lines の挙動を知りたい](../../raw/kozaneba-forum-jp/解決:Add_Linesの挙動を知りたい.md) で外部ユーザ `sta` が 2022-08-10 に「左右の中点で左右グループに分割→左から右に線を引く」アルゴリズムが直感に反すると報告。nishio は「線を引く機能は今後改善したいと思っていますが、**大手術になる**と思います」と返答した。

2023-02-06 のリリース(左右判定を bounding box の重心 → midpoint に変更)はこの混乱への部分的な応答だったが、`sta` の根本的な疑問「2 から 1, 4, 3 に引きたい場合の操作モデルがピンと来ない」は解消されていない。これは現在(2026-06)の「**線ラベル機能の動線がよくわからん**」感覚と地続きの「線の入力 UX が一貫しない」問題系。

## 「default で線が増えない方を選ぶ」原則

[Remove Split-Kozane feature](../../raw/kozaneba-forum/Remove_Split-Kozane_feature.md) (2023-02-27) で明文化:

> デフォルトで線が増える仕様と、増えない仕様とを選べる場合、増えない方を選んでいると言えます。人間は線が多すぎると混乱するので、増えない方が良いと思っています。

これは Edit Kozane の挙動 (single line → 線維持 / multi-line → 線消える)、Clone の挙動 (新規追加なので線無し) の選択に通底する原則。「**線は意図して引くもの、勝手に増えるべきではない**」という基準が辺ラベル UX 検討の隠れた制約になる。

## 「線」概念そのものの限界(2026-05)

[raw/関係UI議論_GPT.md](../../raw/関係UI議論_GPT.md) Round 2-3 の議論では、そもそも **線(エッジ)モデルが関係を表す形式として貧しすぎる** という根本批判が出た:

> 毛玉とは、リッチな関係構造を、単一種類の二項線分に射影した結果である。

線という UI 部品は本質的に二項関係を想定させる。[N項関係](N項関係.md) として実装しても、UI は「複数項を結ぶ線」に近いものになりがちで、本来必要なのは [関係場](関係場.md)(状況から側面が持ち上げられる過程を保存する単位)である、という議論。

Kozaneba での具体的な含意:

- 「線を引く」操作 → 「関係場を作る / 既存の関係場に項を加える」操作
- 線の本数 → 関係場の数
- 毛玉 → 二項投影の症状であり、表・カード・議論マップなど別の射影に切り替える対象
- 線をクリック → 関係場カードを開く

詳細は [関係を第一級にする](../themes/関係を第一級にする.md)、[Clean Relation Elicitation](../themes/Clean_Relation_Elicitation.md)、[関係場](関係場.md) を参照。

## 2026-06: 16 ツール文献サーベイで改修案を具体化

[線UIサーベイ 2026](../themes/線UIサーベイ_2026.md) で外部ツールを 6 系統に分類した結果、Kozaneba 改修の優先度が以下に整理された:

1. **「複数選択 → 線」UI は強みとして守る** — mainstream に近い実装がほぼ無い貴重さ(1:N の親子関係表現で実証済み)
2. **Miro / FigJam 型の軽い 1:1 操作を併存追加** — ホバー時の 4 方向ハンドル + FigJam quick-create(新付箋スポーン + 結線)で思考の連続性を切らない
3. **辺ラベルは「後から double-click」または「描いた瞬間 inline caret」** — modal dialog は採らない(押し付けにならない)
4. **N項関係はジャンクションノード描画** — `items[]` データのまま中央ジャンクション + 放射状の線にレンダリング切替、hypergraph 研究の bipartite 表現と対応
5. **Kinopio 型 connection-type を検討** — 既存 `label: string?` に `type_id` を足し、ユーザが育てる constrained vocabulary(supports / contradicts / ...)
6. **「線を引かない」道(Tana 型)は別軸として保留** — [関係を第一級にする](../themes/関係を第一級にする.md) の延長で別途設計
