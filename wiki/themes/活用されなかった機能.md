## このテーマの問い

[Kozaneba](../entities/Kozaneba.md) に過去に「こうしたら良いだろう」と思って実装したが、実際にはあまり活用されていない機能がある。これらは「技術スタックの陳腐化」ではなく **設計判断の陳腐化** であり、Canvas 化や作り直しを検討する際に「**移植しない決定をするチャンス**」を提供する。

本ページは [Canvas移行の検討](Canvas移行の検討.md) と並ぶ判断材料として、活用されなかった機能の共通パターンを抽出する。

## 個別事例

### 1. N項関係としての線

[線を引く機能](../concepts/線を引く機能.md) は、内部実装としては「N 個の要素の関係」([N項関係](../concepts/N項関係.md))を扱える設計になっている。

- **設計時の意図**: 1:1 に限らない関係も表現できるべきだから
- **実際に必要だったもの**: 大部分のケースで欲しいのは別のもの
  - 「1:N で同じ性質の矢印が発生する」(目次の章と節の関係など)
  - もっと単純な 1:1 関係
- **結果**: 一般化しすぎた N項関係の UI は使いにくい

**さらに深い理由(2026-05)**: [raw/関係UI議論_GPT.md](../../raw/関係UI議論_GPT.md) Round 3 で Gendlin と照合した議論によれば、N項関係はそもそも「項が先にあって関係がそれらを結ぶ」という形式主義を残しており、思考の初期段階(項自体が状況からの分節として現れる過程)を扱えない。実用UIは「項を先に立てる」入力フォームになりがちで、ユーザの実際の思考過程と噛み合わない。解決方向は [関係場](../concepts/関係場.md) と [Clean Relation Elicitation](Clean_Relation_Elicitation.md)。

### 2. グループを囲んで畳む機能

[こざね法](../concepts/こざね法.md) / [KJ法](../concepts/KJ法.md) の「[表札をつけて束ねる](../concepts/表札をつけて束ねる.md)」を素直にデジタル化した機能。

- **設計時の意図**: 紙の操作の電子化。紙では再配置が高コストなので「畳むプロセス1回、開くプロセス1回」で済んでいた
- **実際に起きたこと**: デジタルで簡単に開閉できるようにしたら、新たな問題が発生
  - 開いているものを閉じたら隙間が空く
  - 隙間を手作業で埋めると、次に開いた時に被ってしまう
  - グループの開閉と周囲との関係を整合性を持って扱えるビューではなかった
- **結果**: 後に「大きな付箋」機能がついて、ズームアウトを [なめらかな畳まれ](../concepts/なめらかな畳まれ.md) とみなす運用に流れた。ただしそれもごちゃごちゃして最適ではない。

### 3. 辺ラベルがない線

[線を引く機能](../concepts/線を引く機能.md) は当初「関係がある」ことだけを示す仕様だった。[辺ラベル](../concepts/辺ラベル.md) は無い。

- **設計時の意図**: シンプルに「関係の存在」を表現
- **実際に必要になったもの**: 概念マップ用途で「(始点, 関係の種類, 終点)」の三項関係が必要
- **2025 年の試み**: [Devin](../entities/Devin.md) に辺ラベル機能を実装させたが、線を引くたびにダイアログが出るのは「明らかにウザい」ので作成時 UI は不採用。エッジへのイベントリスナーが無く、通常の UI で辺を対象にしたアクションができないという問題も判明。

## 共通パターン: 一般性を予約した仕様が、実際の使われ方に負ける

3 つの事例に共通するのは「**汎用性を意識して設計した機能が、ユーザの実際の操作モデルとずれていた**」こと:

| 機能 | 予約した一般性 | 実際に使われた特殊化 |
|---|---|---|
| N項関係の線 | 任意の N 個の関係 | 1:1 / 1:N(同性質) |
| 囲んで畳む | 任意のグループの開閉 | ズームアウト([なめらかな畳まれ](../concepts/なめらかな畳まれ.md))による連続的圧縮 |
| 辺ラベル無しの線 | 「関係がある」のみ | (始点, 関係種別, 終点)の三項関係 |

これは典型的な YAGNI(You Aren't Gonna Need It)とは少し違う。**機能を実装したこと自体は正しい**(線も、グループ畳みも、繰り返し言及される中核機能)。問題は **仕様の抽象度** にあり、「より一般的な方が良い」という直感が実用パターンと噛み合わなかった。

## Canvas 化 / 作り直しへの含意

[Canvas移行の検討](Canvas移行の検討.md) を「DOM → Canvas の機械的移植」として行うと、これら 3 つの陳腐化した仕様もそのまま運ばれてしまう。

判断の機会として:

- **N項関係 UI**: 移植せず、1:1 と 1:N(同性質グループ)の 2 種類に分けた特殊化 UI に置き換える。さらに踏み込むなら [関係場](../concepts/関係場.md) ベースの設計に転換し、UI 側では関係を Lift / Gather / Formulate / Project / Carry forward の5操作で扱う([Clean Relation Elicitation](Clean_Relation_Elicitation.md))
- **囲んで畳む**: 紙メタファーから離れ、ズーム/縮尺ベースの連続的圧縮を一級市民にする(物理的開閉ではなく)
- **辺ラベル**: 「線=関係の存在」ではなく「線=(関係種別を持つ)エッジ」を最初から設計に組み込む

これは [断片中心から関係中心へ](断片中心から関係中心へ.md)・[関係を第一級にする](関係を第一級にする.md) で扱う重心移動とも繋がる。

## 4. Split-Kozane(2023-02-27 に実際に削除済み)

「使われずに残った」とは異なる別パターンとして、**実装後に意図的に削除された機能** もある。Split-Kozane (こざねを分割する機能) は 2021-08-13 に追加されたが、2023-02-27 のリリースで Tear / Merge の追加と同時に削除されている([Release Notes 2021-2025 要約](../sources/release-notes-2021-2025.md))。

- **2021-08-13**: Split-Kozane 機能追加 (kozane を 2 つに分割)。設計判断ログでは「**[中間からのスタート](../themes/設計判断ログ.md)**」のトップダウン操作として位置付けられていた
- **2021-08-30**: KozaneMenu に edit/clone を追加した際の note「`if you don't feel the need to keep split after using it for a while, I plan to remove it.`」 — 当初から削除の可能性を含んだ機能だった
- **2023-02-27**: Tear (線で繋がった kozane を分離) / Merge (複数 kozane を統合) を追加すると同時に Split-Kozane を撤去

つまり Split は「**一般化された分割**」(任意の kozane を 2 つに) として実装されたが、実際に使われる操作は「**線で繋がっているものを分ける** (Tear)」「**選択したものをまとめる** (Merge)」という別形式だった。これは前 3 事例と同じ「**一般性を予約した仕様が、実際の使われ方に負ける**」パターンの 4 つ目の事例として読める。

ただし他 3 事例と違い、Split は **実際に削除された**。Canvas 化や次世代設計を待たずに削除できたのは、Tear / Merge が同時に追加されて代替が成立したから。**「代替が用意できれば削除できる」** は他 3 事例にも適用可能な学び。

### 「default で線が増えない方を選ぶ」原則

公開フォーラム [Remove Split-Kozane feature](../../raw/kozaneba-forum/Remove_Split-Kozane_feature.md) で nishio が同日(2023-02-27) に明文化:

> If you have a choice between a default specification with more lines and a default specification with no lines, you can say that you choose the one with no lines. I think it is better not to increase the number of lines because people get confused when there are too many lines.

これは「**線・畳む・辺ラベルの一般化が実用に負ける**」パターンの **後ろ向きの自己定理化** と読める。「より一般的な機能 = より親切」という直感を捨てて、「**人間が混乱しない方を default にする**」という非対称な選択を意識化している。

Edit Kozane / Clone / Split の挙動分岐にもこの原則が現れる:
- Edit Kozane で single line → 元の kozane を残して text 編集、線維持
- Edit Kozane で multi-line → 元の kozane を削除、複数 kozane に分割、線は失われる
- Clone → 新規追加、線はつかない

「**線は意図して引くもの、勝手に増えるべきではない**」が辺ラベル UX 設計の隠れた制約になる。これは現在(2026-06)nishio 本人が辺ラベル機能について「動線がよくわからん」と感じている理由の一つでもあり、「描く瞬間 modal を出すと『勝手にラベルを要求』が押し付けに見える」ジレンマと地続き。

## 2026-06: 外部実装サーベイで「次の改修案」が具体化

3 つの「活用されなかった機能」それぞれに、文献ベースのサーベイで具体的な後継案が出た:

- **N項関係 UI** → [線UIサーベイ 2026](線UIサーベイ_2026.md): データ層は現状のまま、レンダリングを **中央ジャンクション + 放射状の線**(hypergraph 研究の bipartite 表現)に切替。さらに **Miro / FigJam 型ホバーハンドル**で軽い 1:1 を併存、**Kinopio 型 connection-type** で関係を typed にする
- **囲んで畳む** → [畳むUIの再設計](畳むUIの再設計.md): group を **自前 bounding rect を持つ frame に格上げ**(tldraw / Figma frames 型)、これで隙間問題は解ける。**Heptabase 型 inverse-zoom title** で semantic zoom を一級化、**AI 自動表札**(Notion AI 型)で書く負担を消す、**Magic Lens** で「開かずに覗く」
- **辺ラベル無しの線** → [線UIサーベイ 2026](線UIサーベイ_2026.md): 「描いた瞬間 modal」を「**描いた瞬間 inline caret**(Whimsical / FigJam 型)」または「**後から double-click**(Miro / Obsidian 型)」に置き換える。データモデル(`label` フィールド)は既にある

つまり 3 つの陳腐化した仕様すべてに対し、**2025-26 の外部実装からの具体的な後継案** が用意された。Canvas 化と独立にこれらの差し替えを進められる。
