## 起源

[Plan B 試行 2026-06](Plan_B試行_2026-06.md)(辺ラベル UI を Codex に委託)が「自動テストは pass、人間が触ると動かない」状態で merge された経験から、**spec writer (LLM)** と **AI Agent (Codex)** の双方が何を踏み外したかを記録する。

仮説「賢い AI Agent は過去の実装の悪いところを簡単に直す」の検証は、**spec / 検証 / 委託のフレームが整っていない状態では正しく測れない**ことが本質的な学び。本ページはそのフレームをまとめる。

## 何が起きたか(短く)

1. nishio が「辺ラベル UI が無い」と問題提起
2. 私(spec writer LLM)が `wiki/themes/Plan_B試行_2026-06.md` に spec を書いた
3. Codex が spec 通りに実装、Cypress テスト追加、すべて pass
4. main に merge、`9e7122b` ほか
5. nishio が実ブラウザで触る → **double-click しても editor が開かない**
6. 原因調査: 親 SVG の CSS `pointer-events: none` が子要素の SVG attribute を上書き → hit area が実ブラウザでは無効
7. さらに掘る: 仮に修正しても **線を click 可能にすると kozane drag が妨害される**(2021-09 確定の設計原則)を破る = どう直しても spec が間違っていた
8. → 線UI 全体を再設計しないと辺ラベル問題は解けない([線UI再設計 2026-06](線UI再設計_2026-06.md))

## spec writer (LLM) 側の踏み外し

### S1. 形容詞で複数案の優先順位を決めた

spec で「**後から double-click (Miro / tldraw 型) — 最も安全**」と書いた。「最も安全」の判定根拠は提示せず、結果として:

- Miro/tldraw の世界観(線 = 第一級操作対象)と Kozaneba の世界観(線 = 装飾、kozane = 操作対象)の違いを無視した
- 「安全」の意味が AI Agent 側で曖昧になり、drag 不変条件への配慮無く 16px hit area が選ばれた

**自戒**: 案を並べるなら **判定軸を明示**し、Kozaneba 固有の不変条件(drag / モードレス / 装飾を増やさない)を **冒頭で hard constraints として書く**。他ツールの定番パターンを「定番だから安全」と書かない。

### S2. 設計判断ポイントを丸投げした

spec で「どれを採用するかは AI Agent の判断に任せる。判断理由を PR 説明に書くこと」と書いた。これは:

- Kozaneba の設計史(2021-09 `all lines are now non-clickable` 等)を Agent が読んでいる前提だが、その前提を満たす保証は無い
- 結果、Agent は wiki/release notes を読まずに「無難そうな」実装(線全長 hit area)を選んだ

**自戒**: 「Agent に任せる」と書くのは、**任せて良い軸** に限る。Kozaneba 固有の歴史的選択がある軸(drag 不変条件、線の装飾密度、N項関係の扱い)は spec で **決め切る** か、**禁止事項として書く**。

### S3. 自動テスト設計の指示を欠いた

spec の成功条件に「既存テスト(Jest / Cypress)が壊れていない」を入れたが、**新規追加テストの設計指針**を入れなかった。結果:

- Codex は `cy.testid(...).dblclick({ force: true })` で実ブラウザの hit testing を完全バイパスするテストを書いた
- テストは pass、機能は動かない、という最悪の状態

**自戒**: UI 機能の spec には「Cypress / Playwright で `force: true` 系の hit testing バイパス flag を使わない」「実 DOM の click が target に届くことをテストする」を **明示**する。

### S4. 「人間検証」を成功条件に入れなかった

spec のチェックリストに `npm test` / `cypress run` / `npm run build` は入れたが、「**人間が実ブラウザで触り、思考フローを止めずにラベル付けできること**」は入れなかった。

**自戒**: UI/UX 変更の spec には **「人間が実ブラウザで実際に使ってみる」** を **完了条件の頂点**に置く。CLAUDE.md にも:

> For UI or frontend changes, start the dev server and use the feature in a browser before reporting the task as complete. ... Type checking and test suites verify code correctness, not feature correctness — if you can't test the UI, say so explicitly rather than claiming success.

→ spec template に組み込む。

## AI Agent (Codex) 側の踏み外し

### A1. wiki / release notes / 設計史を読まなかった

spec が指す関連ページ([辺ラベル](../concepts/辺ラベル.md) / [線を引く機能](../concepts/線を引く機能.md) / [release-notes-2021-2025](../sources/release-notes-2021-2025.md))に、線 hit と drag 妨害のトレードオフは記述済みだった。Codex はこれを読まずに hit area を実装した。

**含意**: AI Agent への spec で「これらの設計史 page を読んでから実装方針を提示せよ」を明示するか、関連箇所を spec 本文に **抜粋して埋め込む**。

### A2. 自動テストで「実ブラウザを再現していない」ことに気づかなかった

`{ force: true }` を使うことで「hit testing をバイパスしている」事実は Codex は理解していたはず。だが「**自動テストが pass = 機能が動く**」と完了宣言した。

**含意**: AI Agent 自身が「`force: true` を使わざるを得なかった」ことを **報告必須項目** にする。報告があれば spec writer / 人間が「それは実機検証が別途必要」と判断できる。

### A3. 「commit 瞬間が無い」設計上の本質に手を出さなかった

辺ラベル UI が「ラベル無し既存線への後付け」が困難な根本は、**線描画 flow に commit 瞬間が無い** ことだった([線UI再設計](線UI再設計_2026-06.md))。Codex は spec が指した「既存線の double-click」だけ実装し、より根本の設計に踏み込まなかった。

これは Agent の責任ではなく、**spec の scope が狭すぎた** こと。S2 と裏表。

## 仮説検証への含意

「賢い AI Agent は過去の実装の悪いところを簡単に直す」の検証は、以下が揃って初めて意味を持つ:

1. **spec writer (LLM/人間)** が hard constraints を漏れなく書ける
2. **AI Agent** が設計史を読み、自動テストの限界を報告する
3. **自動テスト** が実ブラウザ hit testing を含む
4. **人間検証** が完了宣言の前段にある

Plan B 試行の Codex 1 ラウンドは (1)(3)(4) が欠けていたので、**仮説は測れていない**。次回試行で上記を揃え、その後の感触を取る。

## spec template への組み込み事項

次回以降、AI Agent に Kozaneba 改修を依頼する spec には以下を埋める:

```markdown
## Hard constraints (Kozaneba 固有、絶対に破らない)
- kozane body の drag は移動(常に)
- default で線/要素が増えない方を選ぶ
- モードレス志向(toolbar での明示的モード突入を避ける)
- 他: 該当する設計史 page を列挙

## 関連設計史(実装前に読むこと)
- [辺ラベル](...) / [線を引く機能](...) / [release-notes-2021-2025](...) など
- 抜粋: <重要な原則を 1-2 行で本文に貼る>

## 自動テストの制約
- `cy.click({ force: true })` / `dblclick({ force: true })` を **禁止**(hit testing バイパス禁止)
- 実 DOM のイベントが target に届くことをテストする
- `force: true` を使わざるを得ない場合は、その旨と「人間検証が別途必要」を **報告必須**

## 完了条件(順序付き、上から)
1. 人間が dev server で実ブラウザを起動し、機能を実際に使う
2. 思考フローを止めずに使えることを確認
3. 既存 Jest / Cypress / build が壊れていない
4. 新規テストは hit testing バイパスを使っていない
5. PR 説明に「どの hard constraint を意識して、どの設計選択をしたか」を記述
```

このテンプレートは [Plan_B試行 2026-06](Plan_B試行_2026-06.md) の 2 回目試行で実適用する。

## メタ含意 — LLM/AI Agent と人間の協業分担

| 段階 | 主担当 | LLM/Agent が担うこと | 人間が担うこと |
|---|---|---|---|
| Spec 起草 | LLM | 既知の設計空間を列挙、外部ツール比較 | hard constraints の確定、過去の判断との照合 |
| Spec 査読 | 人間 | — | 「不変条件が漏れてないか」「形容詞で押し切ってないか」のレビュー |
| 実装 | AI Agent | コード生成、自動テスト | scope の境界判定 |
| 自動テスト査読 | LLM | `force: true` 等の hit testing バイパス検出 | — |
| 人間検証 | 人間 | — | 実ブラウザで触る、思考フローの体感判定 |
| 完了宣言 | 人間 | — | 上記すべてが揃ってから |

「LLM/Agent が偉い」「人間がボトルネック」のどちらでもなく、**それぞれが見える / 見えないものが違う**。spec 起草と査読の往復で hard constraints を埋め、実装後に人間検証を必ず挟む、というフレームが Plan B 試行から得た学び。
