## 経緯

[Plan B 試行 2026-06](Plan_B試行_2026-06.md) で「辺ラベル UI」を Codex に投げたが、

- Cypress テストは `{ force: true }` で hit testing をバイパスして pass
- 実ブラウザでは double-click が editor を開かない
- 原因は親 SVG の CSS `pointer-events: none` が子要素の SVG attribute を無効化していること
- 仮に修正しても **「線を click 可能にすると kozane drag が妨害される」**(2021-09 `949a1fd: all lines are now non-clickable` で確定した設計原則)を破る

→ 辺ラベル UI 単独の小修正では不十分。**線生成 UI 全体を再設計**し、その流れの中でラベル/線種/相手間違いの修正動線を統一的に扱う必要がある。

本ページはその統一設計案。AI Agent に渡せる仕様としてまとめる(次の試行の入力)。

## 不変条件(hard constraints)

1. **kozane body の drag は移動**(常に、例外なし)
2. **default で線が増えない方を選ぶ**(誤生成しにくい)
3. **モードレス志向**(toolbar での明示的モード突入を避ける)
4. **mainstream UI を増やしすぎない**(線にデコレーション/常時表示要素を増やしすぎない)
5. **iPad はセカンドプライオリティ**(まず PC で完成、touch は後付け)

## 既存実装の問題(再設計対象)

| 既存 | 問題 |
|---|---|
| toolbar で line mode に切替 → click 始点 → click 終点 → 次の起点待機 | モード切替コスト。「kozane を動かす」と排他 |
| 線種(line / arrow / double_heads / double_lines / delete)を toolbar で **事前** に選ぶ | pre-decision overload。引きながら決められない |
| 線を引き終わった瞬間 = **次の線の起点待ち** | **commit 瞬間が存在しない** → label / 線種訂正 / 相手訂正の動線がすべて後付けで困難 |
| 既存線への hit は `is_clickable` フラグ(現状 hardcoded false) | 後修正の経路が事実上無い |

ラベル問題は「commit 瞬間が無い」ことの一症状。本再設計はそこを起点に解く。

## 再設計の中心アイデア

> **hover anchor → drag → release で線確定 → release 後は「編集 window」に入る → 任意のアクションで離脱 = commit**

### 1. 描画フロー: hover anchor + drag

- **kozane に hover** すると縁(または周囲)に小さな anchor 表示
  - 視覚は控えめ(Kozaneba の「装飾を増やさない」哲学に合わせて、Miro より控えめな表示)
  - 候補: 4 方向の小点 / 周囲 ring / 控えめな `+` / hover 中だけ薄く表示
- **anchor から drag** で線描画開始
  - drag 中、ターゲット候補 kozane を highlight(detail は後で詰める)
  - kozane body の通常 drag(移動)とは start 位置で完全に区別 = drag 不変条件維持
- **別 kozane で release** → 線確定 → **編集 window** に入る
- 空中で release → 何も起きない(default で線が増えない方を選ぶ)

### 2. 編集 window(post-release, pre-commit)

release 直後、線は **active な編集状態に留まる**:

```
[kozane A]━━━━━●━━━━━[kozane B]
              │
        ┌─────┴─────┐
        │ [✎ label]  │   ← inline caret(autofocus)
        │ ─ → ↔ = 🗑 │   ← 線種 chip(現 type を highlight、🗑 = 削除)
        └───────────┘
   ●               ●
   (handle)        (handle)
```

このウィンドウ中:

- **キーボード入力** → label に流れる(空のまま離脱すれば label 無し)
- **線種 chip の click** → 線種を切替(`heads[]` / `is_doubled` の組合せを書き換え)
- **endpoint handle の drag** → 別 kozane へ drop で endpoint 差し替え = **相手間違いの修正**
- **🗑 click** → 線を消す(誤って引いてしまった時の即取消)

ホットキー(rotate / spread / 他)は編集中は無効化(既存 `disableHotKey` を流用)。

### 3. 離脱 = commit ルール(統一)

「離脱イベント = 編集 window を抜けて passive 状態へ確定」を **一つのルール**として定義する。

**commit する離脱イベント**:
- 別の kozane / 線 / 空間を click
- 別の hover anchor から drag を始める(= 次の線の描画開始)
- kozane body の drag(= 移動の開始)
- canvas pan / scroll / wheel / pinch zoom
- toolbar / menu の任意の操作
- Esc / Enter
- 編集対象外のホットキー入力

**commit しないアクション(編集状態に留まる)**:
- caret に文字入力 / Backspace / 矢印キー
- 線種 chip の click
- endpoint handle の drag(retarget 中)
- ラベル text / chip / handle / editor 自体の click
- マウスを動かすだけ(hover、無 click)

「キャンセル」semantics は別途持たない。離脱は常に commit。やり直しは:
- 編集 window 中 → 🗑 chip で削除
- 編集 window 後 → **Cmd+Z (undo)** で線創出ごと巻き戻す

### 4. passive 線への再編集(commit 後)

「描画から時間が経って間違いに気づいた」場合:

| 線の状態 | 編集 window 復帰の起点 |
|---|---|
| **ラベルあり** | ラベル text を click → 同じ編集 window へ |
| **ラベルなし** | 線の **中点に最小 affordance**(4x4 px の控えめな点)→ hover で 20x20 hit zone に拡張 → click で編集 window へ |

線の中点は構造的に kozane と kozane の **間の空間** にあるため、小さな中点 affordance は **drag 不変条件をほぼ完全に維持**する(Miro/FigJam も同様の妥協を採用)。

復帰先は **新規描画後の編集 window と同じ UI**。学習負荷も実装複雑度も最小。

## データモデルへの影響

[コード構造調査](../sources/kozaneba-code-architecture.md) より、`RTLineAnnot` は既に必要なフィールドを持つ:

- `label: String.optional()` — 2025-09 で追加済み
- `items: Array(RTItemId)` — N 項対応
- `heads: Array(RTArrowHead)` — endpoint ごとの矢印
- `is_doubled: Boolean` — 二重線

**新フィールド不要**。再設計は UI 層のみで完結する。

新たに必要なグローバル状態(`initializeGlobalState.ts` への追加):
- `line_edit_state: null | { annot_index: number, ... }` — 編集 window が active な線(既存の `editing_line_label` を一般化)
- 既存の `line_type: TLineType` は toolbar から消す候補(編集 window の chip に移譲)

## スコープ外(本仕様には含めない)

- **N項関係 UI**(items.length > 2): 編集 window から endpoint を追加する動線は将来拡張。今回は 2 項のみ
- **iPad / touch 対応**: hover が無いため別 gesture が必要。本仕様には含めず、後続で扱う(参考: [iPad実機対応調査_2026-06](iPad実機対応調査_2026-06.md))
- **AI による線・ラベル提案**: 別問題。[Clean Relation Elicitation](Clean_Relation_Elicitation.md) / [広聴AI](../concepts/広聴AI.md) 側で扱う
- **線描画モード(toolbar)の完全廃止**: 既存ユーザの慣れも考えると、当面は併存させ、新動線が定着したら検討

## 既存 UI への影響

- toolbar の line/arrow/double_heads/double_lines/delete ボタン → 残置でよい(後方互換)。だが新動線が定着したら段階的に縮小
- Codex が 9e7122b で入れた既存ラベル編集(`is_clickable` + double-click + foreignObject)→ **本再設計に置き換え**。既存実装は中点 affordance 経由の編集 window 復帰として再利用
- AnnotationLayer の SVG root の `pointerEvents: "none"` → 維持。新動線は `pointerEvents: "auto"`(CSS) の小さな affordance(anchor / 中点 dot / label text)が個別に hit を取る形

## AI Agent に渡す前のチェックリスト(自戒)

[AI委託の設計と検証 2026-06](AI委託の設計と検証_2026-06.md) で議論した、spec writer 側の自戒:

- [ ] 不変条件(drag 不変条件 / モードレス志向 / etc)を **冒頭で明示**
- [ ] 「最も安全」「定番」のような形容詞で複数案の優先順位を決めない(Kozaneba 固有制約とぶつかる)
- [ ] 自動テスト(Cypress)に `{ force: true }` を使わない指示を明記。**人間検証なしに完了宣言しない**
- [ ] 「人間が実ブラウザで触って思考フローを止めないこと」を成功条件に明記
- [ ] 既存設計原則([辺ラベル](../concepts/辺ラベル.md) / [線を引く機能](../concepts/線を引く機能.md) / [活用されなかった機能](活用されなかった機能.md))への参照を spec に埋める
