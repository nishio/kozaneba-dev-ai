## このテーマの問い

2025-08-29 に [Canvas プロトタイプ](Canvas_1万件デモの拡張.md) の開発が止まった原因の一つは、**クラスタの分け方** で nishio が悩んだことだった([pKozaneba2025-08-29](../../raw/scrapbox_kozaneba/2025-08-29__pKozaneba2025-08-29.md)):

- **連結成分方式**: 矩形選択がオーバーラップする、マージ閾値(3 割 / 2 割)で連鎖マージが起きる
- **10 マス割り方式**: 「自然なクラスタが分割されてしまうことは起こる」

両者とも欠点があり、結論なし。**「自然なクラスタを尊重しよう」と「グリッドで切ろう」のどちらも良し悪し** があった。

2026-06-03 に nishio が出した着地方向: **「Google Maps のメタファで開き直る」**。分割されてもいい、タイル方式でいい、と認める。

## Google Maps メタファの中身

Google Maps は世界地図を **固定の経緯度グリッド** でタイル化している:

- 東京都が複数タイルにまたがって表示される → ユーザは混乱しない
- なぜなら **タイルは中身の意味とは独立した uniform な区切り** だと暗黙に理解しているから
- 「正しい行政区画」を再現することを諦めて、**メタファとして合意されている区切り** を借りている

これをプロトタイプの 1 万件付箋に適用すると:

- 意見テキストの UMAP 座標を 10x10(あるいは N×N)のタイルで割る
- 自然なクラスタがタイル境界で分割されても、それは Google Maps と同じ「タイルだから」で受容される
- マージ閾値が要らない、連鎖マージも起きない、完全に予測可能

## 連結成分 vs グリッドの比較

| | 連結成分 + マージ閾値 | グリッド(Google Maps 型) |
|---|---|---|
| 形 | データに合わせて変形 | 固定 |
| 「自然なクラスタ」 | 尊重しようとする | 分割を許容 |
| マージ閾値 | 必要(連鎖マージの悩み) | 不要 |
| 予測可能性 | 創発的、デバッグ困難 | 完全に予測可能 |
| ズーム動作 | 各クラスタが固定サイズ | **ズーム = タイル粒度切替**(Google Maps の挙動と一致) |
| ユーザ受容 | 「なぜこの切り方?」と聞かれる | 「タイルだから」で済む |
| AI 表札 | クラスタごとに 1 つ | **タイルごとに 1 つ**(ズームレベルで再生成) |

## [認知メタファのデザイン](認知メタファのデザイン.md) の延長

[認知メタファのデザイン](認知メタファのデザイン.md) で抽出した原則:

1. 対象ユーザが既に持っているメタファを使う
2. 抽象度を上げない
3. 副産物として高機能になるのは OK

Google Maps は **世界中で日常的に使われている可視化** で、付箋メタファ([密度の高さを大きさに変換して可視化](../concepts/密度の高さを大きさに変換して可視化.md))と並んで認知コストがほぼゼロ。「タイルが切り替わる」「ズームで詳細度が変わる」「ピン / アイコンで概観する」は説明不要。

しかも Google Maps メタファは **タイルの境界が意味を持たない** ことを既に教えている:**「この切り方は何の意味?」という問いをユーザが投げない**。これは KDE 等高線が「データサイエンティスト向けで一般人には伝わらない」と却下されたのと正反対 — Google Maps は最強の一般人向けメタファ。

## [人間が動かすから隙間ができる](人間が動かすから隙間ができる.md) への第三の道

このページで論じた二分法:

- **人間駆動(本流 Kozaneba)**: 隙間に意味がある
- **アルゴ駆動(プロトタイプの連結成分案)**: 隙間に意味がない、それが問題

これに対する **第三の道**:

- **タイル駆動(Google Maps 型)**: 隙間 / 境界に意味は無いが、**メタファとして合意されているので問題にならない**

つまり「アルゴ駆動の隙間に意味を与えよう」(連結成分が目指していた方向)を諦めて、**「タイルだから」というメタファで意味の欠如を正当化** する解法。アルゴ駆動側で空間意味を作る代わりに、ユーザが既に持っているタイル理解を借りる。

これは [物理演算](../concepts/物理演算.md) の「機械が動かしてはいけない」禁忌とも整合的: **タイルは「動かしている」のではなく「区切っている」だけ**(配置は元のままで、表示単位が切り替わるだけ)。

## semantic zoom との接続

Google Maps のズームは典型的な semantic zoom + tile system:

```
ズームレベル 1: 国レベルのタイル(各タイル = 国名 + アイコン)
   ↓
ズームレベル 2: 都市レベルのタイル(各タイル = 主要都市 + 道路)
   ↓
ズームレベル 3: 通りレベルのタイル(各タイル = 通り名 + 店舗)
```

これをプロトタイプに適用すると:

- ズームレベル N: 大きいタイル、各タイルに AI 要約 1 つ(coarse 表札)
- ズームレベル N+1: 小さいタイル、各タイルに AI 要約 1 つ(fine 表札)
- ズームレベル ∞: タイル消滅、個別付箋表示

**AI 表札がズームレベルごとに別物として precompute される**。プロトタイプの `clusters_summary.json` が `tiles_zoom1.json / tiles_zoom2.json / ...` の階層構造に変わる。これは [畳むUIの再設計](畳むUIの再設計.md) の Heptabase 型 inverse-zoom title を **より定式化** した形:**ズームレベル = タイル解像度 = 表札粒度** が一貫した 3 連動になる。

## 本流 Kozaneba への含意

本流の小規模ユースケース(1000 件未満)で Google Maps メタファをどう使うか:

- **そのまま使うのは弱い**:1000 件くらいなら人間が空間を作るので、タイル化する動機が薄い
- **大規模ノードを取り込む際の橋渡し**にはなる:本流に「[広聴AI](../concepts/広聴AI.md) のデータを取り込む」ような場面があれば、タイル化された AI 要約として表示する選択肢
- **空間ナビゲーション操作の参考**:Google Maps のドラッグパン、ピンチズーム、ダブルタップで拡大、検索 → ピン、はそのまま本流の操作に転用可能

つまり「本流の中心機能を変える」のではなく、「**大規模データを本流に登場させるときの表現方法**」として活きる。これは [3 Plan 議論](3plan議論.md) の Plan A(新規サービス)で「**入口は対話 / 出口はマップ的可視化**」のような構造を取るときの設計テンプレートになりうる。

## 残る判断ポイント

タイル方式に着地したとしても、まだ未解決の判断がいくつかある:

1. **タイル境界の基準**: world 座標(UMAP 後の固定座標)を等分? それとも viewport 座標(画面に対して相対)? Google Maps は world 座標(緯度経度)固定で、これが「同じ場所が同じタイル」を保証する強み。プロトタイプも world 座標固定が自然
2. **タイル粒度の決定方法**: 10x10 / 50x50 / 100x100 の選択。固定?それともデータ密度に合わせて適応?(Google Maps の zoom level は固定の階段)
3. **タイルあたりの最大表示数**: タイル内に N 件あったら表札だけ? それとも N=1〜3 まで全部見せる? AI 表札と「個別付箋を 2〜3 個サンプル表示」のハイブリッドはありうる
4. **隣接タイルの表札衝突**: 同じ話題が複数タイルに分かれた場合、表札が重複する(東京都が複数タイルに「東京都」と書かれる Google Maps と同じ問題)。許容するか、ローカル抑制をかけるか
5. **ズームレベル間の遷移**: 段階的にフェード? それとも瞬間切替? Google Maps は瞬間切替に近い
