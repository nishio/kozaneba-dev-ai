## このテーマの問い

[線を引く機能](../concepts/線を引く機能.md) は [Kozaneba](../entities/Kozaneba.md) の中心機能の一つだが、現状の UI は以下の問題を抱えている(2026-06-01 nishio による観察):

- 初期に「[N項関係](../concepts/N項関係.md) を表現したい」として設計した結果、1:1 の線を引くのに不便な操作になっている
- Miro 型の「ホバー → ハンドル / メニュー → クリック / ドラッグ」のような軽い操作が無い
- 一方で **「複数の付箋を選んでから線を引く」** のは 1:N の親子関係表現で便利だったので残したい

つまり「現状の重い汎用 UI を捨てる」「Miro 型の軽い 1:1 UI を入れる」「複数選択経由の 1:N UI は残す」の三立を、外側のツールはどう解いているかを文献ベースで見る。

## 現状スキーマ(再掲)

[`TAnnotation.ts`](../../work/kozaneba/src/Global/TAnnotation.ts) は `line` 1 種類だけ([kozaneba-code-architecture](../sources/kozaneba-code-architecture.md)):

```ts
RTLineAnnot = Record({
  type: Literal("line"),
  items: Array(RTItemId),          // N 個。データレベルでは N項関係
  heads: Array(RTArrowHead),        // "none" | "arrow", items と並列
  is_doubled: Boolean,
  label: String.optional(),         // 辺ラベルのフィールドはスキーマに既に存在
  custom: { is_clickable, ... },
});
```

データモデルとしては:
- N項関係 OK(`items` の長さ無制限)
- 各端点ごとに矢印頭の有無を独立指定 OK
- 辺ラベル OK(label フィールド存在、入力 UI 未実装)
- ただし `pointerEvents: "none"` でエッジへのクリックが基本的に死んでいる

つまり **UI の貧しさが本質** で、データ層は十分に表現力がある。

## 16 ツールの connection 描画スタイル分類

外側のツールを 6 系統に分類:

### 1. エッジハンドル(磁石型)

**Miro / FigJam / Mural / Obsidian Canvas / Apple Freeform** が代表。付箋にホバーすると 4 方向(N/S/E/W)に小ハンドルが出る。クリックで「隣に新付箋 + 自動接続」、ドラッグで線を引いて別付箋に着地。FigJam の **Quick Create** は青ハンドルから矢印アイコンをクリックして 4 方向に新付箋をスポーン、結線済み。

- 強み: 思考の連続性を切らない、初心者にも明示的。1:N の fan-out 発想に有効。
- 弱み: 1:1 中心。多選択 → 一括接続のような操作は別途必要。

### 2. アンカーポイント(固定型)

**Lucidchart / draw.io / Whimsical** がここ。シェイプ周囲に固定の接続点があり、そこからドラッグ。**直交ルーティング + waypoints** で線が自動で道を選ぶ。

- 強み: プロセス図の整然さ。
- 弱み: 重い、思考整理用途には過剰。

### 3. Sticky / binding arrow(項追従型)

**tldraw / Excalidraw / Apple Freeform**。矢印は **「項を持つオブジェクト」** で、`{terminal, normalizedAnchor, isPrecise, isExact}` のような構造を内部に持つ。シェイプが動くと矢印が追従。Excalidraw は **双方向**(シェイプが arrow を `boundElements` に保持)で扱う。

- 強み: 矢印を first-class object として扱うので、ラベル・スタイル・履歴が自然に乗る。
- Kozaneba 文脈での意義: 現状の `Annotation.items: TItemId[]` モデルにそのまま重なる。データ層改修不要。

### 4. 複数選択 → 一括接続(コマンド型)

**yEd / OmniGraffle / Cytoscape** 系。線を作るのは「選択メニューから *Connect*」というコマンド操作。**yEd は edge bundling**(並行する複数の線を 1 本の幹に視覚的にまとめる)を post-hoc アルゴリズムで提供 — 1:N / N:M の見せ方を整える機能。

- 強み: **これが Kozaneba の現状 UI に最も近い**。1:N の親子関係を一気に作れる便利さがある。
- 弱み: 思考の途中で 1:1 をサッと引くには重い。

### 5. 暗黙的関係(タグ / リンク型)

**Tana / Roam / Logseq**。**そもそも線を引かない**。`[[link]]` や `#tag` を書くと、別途生成される graph view に線が現れる。**Tana の supertag + field** は 「N:M の typed relation」を「フィールド = 関係名」として宣言する、視覚的線なしで関係を構造化する完成形に近い。

- 強み: テキスト編集と並行して関係が積み上がる、可視化と切り離せる。
- Kozaneba 文脈での意義: [関係場](../concepts/関係場.md) / [Clean Relation Elicitation](Clean_Relation_Elicitation.md) と同じ思想方向。線を引く操作を「関係カードを作る」に置換するなら、Tana が最も近い前例。

### 6. テキスト DSL(コード駆動)

**mermaid / D2 / Graphviz / PlantUML**。`A --> B : label` のような構文で書く。**D2 と Graphviz は `lhead` / `ltail` でクラスタ全体への接続を 1 行で書ける** — テキスト側で N項関係を表現する自然な記法。

- Kozaneba 文脈: 線を「文字で書いて自動配置」する道は thought-organizing 用途と相性が悪い(配置自体が思考)。ただし「LLM がテキスト DSL で線案を提案 → 人間が配置」のような併用は面白い。

### ボーナス: Drag-onto(直接操作)

**Scapple**(Literature & Latte の古典)が独特。**付箋 A を付箋 B にドラッグ&ドロップすると接続が toggle される**。ツール切替なし、選択中の付箋にも同じジェスチャ。

- 強み: 学習コストほぼゼロ、習得すれば極めて速い。
- 弱み: ジェスチャの再発見性が低い(ヒントなしでは気付けない)。

## 角度別の発見

### 1. 「複数選択 → 一括接続」は希少

mainstream の visual whiteboard で「**N 個選択 → Connect コマンド → きれいなハイパーエッジ**」を持つツールはほぼ無い。近いのは:

- (a) FigJam の **quick-create**(1 source からの fan-out 用)
- (b) yEd の **edge bundling**(*post-hoc* 視覚集約)
- (c) Tana の **field**(線を引かず構造化)
- (d) text-DSL の D2 `lhead` / `ltail`(クラスタ to クラスタを 1 行)

つまり Kozaneba の「**複数選択 → 線**」UI は **mainstream に近い実装が存在しない貴重なもの** と読める。捨てずに **そのまま強みとして残す** のが妥当。

### 2. 辺ラベル UI の三大パターン

- **描いた瞬間 inline**(Whimsical / FigJam):midpoint に caret が出て、書くかスキップするか即選択
- **後から double-click**(Miro / tldraw / Obsidian Canvas / draw.io):デフォルト無ラベル、ラベルは意図的編集
- **構造的・限定語彙**(Kinopio の `connection-type` / Tana の field):ラベル = type、ユーザが育てる constrained vocabulary

[辺ラベル](../concepts/辺ラベル.md) で問題になった「線を引くたびにダイアログが出るのはウザい」は、**「描いた瞬間 dialog」と「描いた瞬間 inline caret」の差** に該当する。inline caret は「書きたければ書き始める、書かなければ放置」なので押し付けにならない。dialog は modal で押し付ける。

→ **Kozaneba は「後から double-click」または「inline caret」を採るべき**、modal dialog は採らない。

### 3. N項関係 / hypergraph の描画

mainstream には hypergraph 描画はほぼ無い。research / 可視化系では:

- **Polygon / convex-hull 描画**: N項関係 = 多角形、各頂点がメンバー
- **Bipartite / 中間ノード追加**: 「関係ノード」を 1 つ立て、各メンバーと二項線で結ぶ(de facto)
- 文献: [Automatic Polygon Layout for Primal-Dual Hypergraph Visualization (arXiv 2108.00671)](https://arxiv.org/pdf/2108.00671)、[Mixed coordinate node-link visualization for co-authorship hypergraphs (arXiv 2310.19640)](https://arxiv.org/pdf/2310.19640)

**Kozaneba の `items: TItemId[]` モデルは bipartite (中間ノード) 型と直接対応する**。「線」が中央のジャンクション点を持つレンダリングに変えれば、N項関係を 1 個の図形として扱える。これは [関係場](../concepts/関係場.md) を一級オブジェクト化する道とも噛み合う。

### 4. AI が線を提案する: まだ未成熟

Miro AI / FigJam Jambot は **「クラスタ化と要約」までは確実にできる** が、「**信頼できる labelled edge 提案**」はまだプロダクト化されていない。「AI がグループ化、人間が関係付け」が 2026 時点の安定型。

→ Kozaneba で AI を入れるなら、**まず「こざねを束ねる候補」を提案**、次に **「束ねた中の関係名候補」を提案**、線の自動描画は最後。

### 5. 「線を引かない」道(Tana 型)

**Tana の supertag + field** は最も完成度の高い「視覚的線を引かない関係システム」。フィールド = 関係名、値 = 関係先ノード、N:M 自然。Kozaneba で同等のことをするなら:

- こざねに「タグ / 属性」を持たせる
- タグの値が他のこざねへの参照になりうる
- 線はその参照の **後付けの可視化** であって、編集は型 / タグ側でする

これは [関係を第一級にする](関係を第一級にする.md) のテーマと完全に同じ方向。Kozaneba がこの道へ進むなら **線は副産物に降格** する。一方で「2D 空間での発想整理」という Kozaneba 固有の強みからは離れる(Tana は outliner ベース)。

## Kozaneba への含意

優先度順:

### 1. 「複数選択 → 線」は強みとして守る

mainstream 不在の貴重な UI。1:N の親子関係表現で実証済みの便利さがある。**残すだけでなく、UI として強調・発見しやすくする**(現状は埋もれている)。yEd 型の **post-hoc edge bundling** を併用すると、複数の 1:N が累積したときに見やすくなる。

### 2. Miro 型の軽い 1:1 操作を追加(quick-create も込み)

ホバー時に 4 方向ハンドル → クリック / ドラッグの軽い操作を **追加**(既存の複数選択 UI を消さずに併存)。**FigJam の quick-create**(青ハンドル → 矢印クリック → 新付箋 + 結線)も同時に実装すると、「思考の連続性」が崩れない。これは [チュートリアル](../concepts/チュートリアル.md) の選択肢過多問題とは別軸 — 「初心者の最初の動作」を軽くする話。

### 3. 辺ラベルは「後から double-click」を採る

[辺ラベル](../concepts/辺ラベル.md) の失敗(線引くたびに modal)は **inline caret か lazy edit** に置き換える。スキーマ側は label フィールドが既にあるので、変更不要([kozaneba-code-architecture](../sources/kozaneba-code-architecture.md))。`pointerEvents: "none"` の問題は同時に解決する必要がある — 線自体がクリック可能になって初めて double-click による編集が成立する。

### 4. N項関係はジャンクションノード描画に切り替える

データは `items[]` のまま、レンダリングを **中央ジャンクション + 放射状の線** に変える。これで N項関係が「中央の小ノード = 関係本体」「周囲の線 = メンバー」として視覚的に成立。[関係場](../concepts/関係場.md) を一級可視化する道筋にもなる。

### 5. Kinopio 型 connection-type を検討する

`label: string?` を `label: string?` + `type_id: TConnectionTypeId?` に拡張する余地。型は **ユーザが育てる**(supports / contradicts / is-example-of / ...)。色とラベルが連動する。これは未来の AI 提案(「この線は contradicts 型では?」)とも相性が良い。

### 6. 「線を引かない」道は別物として保留

Tana 型の暗黙関係は [関係を第一級にする](関係を第一級にする.md) の延長で別途設計する。線 UI 改修と分離して考える(同時にやるとスコープが爆発)。

## 開いた問い

- 既存の Kozaneba ユーザ(nishio 本人 + 限定ユーザ)が「複数選択 → 線」をどれだけ使っているかは実測されていない。git log や Firestore のデータから集計できるか
- ジャンクションノード描画への切替は、既存データの線を「中央点 = 既存の中点」として automatically migration できる
- connection-type を入れるなら、UI でどう選ばせるか(既存型から選ぶ / 新規作成、Kinopio の実装が参考)
- 「線を引く操作」を [関係場](../concepts/関係場.md) カードを作る操作に置換するなら、線 UI 改修は中継ステップにすぎないのか、それとも別軸として価値があるのか

## 2026-06-03: サーベイ結論の Kozaneba 固有化 = 線UI 再設計

本サーベイは外部 16 ツールから「軽い 1:1 / N項のジャンクション / 描いた瞬間 inline caret / 後から double-click / Kinopio 型 typed connection」など複数案を提示した。これを [Plan B 試行 2026-06](Plan_B試行_2026-06.md) で Codex 実装に落とそうとして「**外部 best practice の直接移植は Kozaneba の drag 不変条件と衝突する**」ことが判明:

- Miro/tldraw 型「後から double-click」→ 線本体への hit が kozane drag を妨害
- Whimsical/FigJam 型「描いた瞬間 inline caret」→ Kozaneba は click-click 描画なので「次の線の起点」と caret が衝突

→ サーベイ案を Kozaneba 固有の文脈で再結晶化したのが [線UI 再設計 2026-06](線UI再設計_2026-06.md)。
- **hover anchor + drag** で線生成(Miro/FigJam 型を kozane body 外で実現)
- **release 後の編集 window** で label / 線種 / endpoint を扱う(commit 瞬間が無かった欠陥の解消)
- **離脱イベント = commit** ルールで全動作を統一
- **passive 線への再編集**は label text / 中点 affordance から同じ window へ復帰

「Kinopio 型 typed connection」「N項関係のジャンクション描画」は今回 scope 外として温存。次回試行で扱うかは別途判断。
