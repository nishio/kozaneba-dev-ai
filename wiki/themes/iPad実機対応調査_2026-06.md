# iPad実機対応調査 2026-06

## 位置づけ

[設計判断ログ 2021](設計判断ログ.md) では、タッチデバイス対応は「iPhone はさておき iPad では動いて欲しい」と書かれていた未解決課題だった。今回、現行 `origin/main` 相当のコードを clean detached worktree `work/kozaneba-ipad-audit` (`d5757f5`) で読み、iPad で「なんかうまく動かない」原因候補を確認した。

結論として、もっとも疑わしいのはキャンバス操作が mouse event 中心に実装されており、touch / pointer event の経路が実質的に接続されていないこと。

## コード上の問題候補

### キャンバスが mouse event 前提

`ItemCanvas` は `onMouseDown` / `onMouseMove` / `onMouseUp` だけを登録している。iPad の指や Pencil の操作では、デスクトップ mouse と同じ連続 event sequence を期待できないため、選択、drag、drop、click 判定が壊れやすい。

`Kozane`、`Group`、`Gyazo`、`Scrapbox` も同じく `onMouseDown` から `onGenericMouseDown` へ入る。主要オブジェクトの操作面全体が mouse 前提になっている。

### touch_support はあるが未使用

`src/utils/support_touch.ts` には `onPointerDown` / `onTouchStart` へ bridge するヘルパがある。しかし `rg touch_support` では定義箇所以外に利用がない。つまり「昔 touch 対応を意識した痕跡」はあるが、現行 UI には接続されていない。

### 座標取得も MouseEvent 前提

`get_client_pos` は `event.clientX` / `event.clientY` だけを見る。TouchEvent の `changedTouches[0]` や PointerEvent の正規化はない。したがって、既存 mouse handler を touch handler に単純転用しても座標が `undefined` になりうる。

`onCanvasMouseDown` も `event.button`、`event.pageX`、`event.pageY` 前提で、iPad の touch event にはそのまま適用しづらい。

### Group drop が hover 依存

`Group` は drag 中の highlight / drop 補助に `onMouseEnter` / `onMouseLeave` を使っている。touch には hover がないため、group へ入れる、group から出す、nested group に drop する操作は iPad で特に壊れやすい。

touch 対応では、hover ではなく pointerup 時の座標、`elementFromPoint`、または world 座標上の bounding box で drop target を決める必要がある。

### touch-action がない

`#canvas` は `overflow: hidden; height: 100%; width: 100%` だが、`touch-action: none` がない。iPad Safari ではブラウザの scroll、pinch、long press、text selection などの既定動作がアプリ操作と競合しやすい。

### Google sign-in は popup 固定

`SignDialog` と `CloudSaveDialog` の FirebaseUI は `signInFlow: "popup"` 固定。iPad Safari、ホーム画面 PWA、Cookie 設定によっては popup 認証が詰まりやすい。ログイン起点の不具合なら、mobile では redirect fallback を検討する。

## 修正方針

優先は mouse handler を増築することではなく、入力イベントを PointerEvent 中心に正規化すること。

- `pointerdown` / `pointermove` / `pointerup` / `pointercancel` を主要経路にする。
- `setPointerCapture` で drag 中の move/up を取り逃がさない。
- `get_client_pos` を MouseEvent / PointerEvent / TouchEvent から同じ `TScreenCoord` を返す関数にする。
- `#canvas` に `touch-action: none` を付け、アプリ内 canvas 操作と browser gesture を切り分ける。
- group drop は hover 依存をやめ、pointerup 時の hit test に寄せる。
- pencil / finger / mouse / trackpad を区別する必要がある場合は `pointerType` を観測してから分岐する。

## 実装メモ 2026-06-03

`work/kozaneba` が dirty だったため、clean worktree `work/kozaneba-pointer-events` に `codex/ipad-pointer-events` branch を作成して実装を隔離した。

実装では `MouseEvent` 前提の座標処理を `TInputEvent` と `get_client_pos` に寄せ、mouse / pointer / touch の座標を同じ `TScreenCoord` へ正規化した。主要な canvas / kozane / group / selection / gyazo / scrapbox の entry point には `onPointerDown` / `onPointerMove` / `onPointerUp` / `onPointerCancel` を追加し、mouse handler は fallback として残した。

drag 中は canvas 側で `setPointerCapture` を使い、pointer が元要素から外れても move/up を取り逃がしにくくした。group drop は hover だけに依存せず、`pointerup` 時の座標から `elementFromPoint` と bounding box fallback で drop target group を判定するようにした。自己 group / 子孫 group への drop は既存の不変条件を壊すため除外している。

`#canvas` には `touch-action: none` と `-webkit-touch-callout: none` を追加し、iPad Safari の scroll / long press などの browser gesture と canvas 操作の競合を減らす方針にした。

検証として、synthetic `pointerType: "touch"` の Cypress spec `test_pointer_events.cy.ts` を追加した。`npm run build`、`npm test`、`npm run codex:preflight`、および `JAVA_HOME=/opt/homebrew/opt/openjdk@21 PATH=/opt/homebrew/opt/openjdk@21/bin:$PATH CYPRESS_BASE_URL=http://localhost:3001 npm run cypress:kozaneba-all` は pass。最後の Kozaneba Cypress は Firebase Auth / Firestore emulator 付きで 18 specs / 34 tests pass。

実装は commit `e517035 Add pointer event input handling` として `codex/ipad-pointer-events` branch に push し、draft PR [#46 Add pointer event input handling](https://github.com/nishio/kozaneba/pull/46) を作成した。

ただしこれは iPad 実機 Safari の完了判定ではない。desktop Electron/Cypress 上で pointer regression を通した段階なので、次の gate はこのページの smoke checklist に沿った iPad 実機確認。

## iPad実機テストの考え方

Cypress は desktop browser 上の E2E には使えるが、iPad Safari の実機 gesture をそのまま検証する道具ではない。iPad 対応の完了判定には、最低限、実機での手動 smoke test が必要。

## iPad実機自動テストの可能範囲

iPad 実機 Safari の自動テストは可能だが、desktop Cypress の延長ではない。

### Cypress

Cypress は現行の Kozaneba required CI には適しているが、iPad 実機 Safari を直接操作する用途には向かない。公式 docs でも native/mobile event support がないこと、対応 browser が主に desktop Chrome / Firefox / Edge / Electron / experimental WebKit であることが示されている。

したがって Cypress でできるのは、viewport を iPad 相当にする、WebKit で近似する、pointer event の unit/integration を厚くする、といった「事前検出」であり、実機の Safari gesture 確認そのものではない。

### Playwright

Playwright は `Mobile Safari` などの device profile で user agent、viewport、screen size、touch 有無をエミュレートできる。Kozaneba では pointer / touch regression の desktop 自動テストを増やす候補になる。

ただし標準 Playwright がローカルに接続した iPad Safari を直接動かすわけではない。実機 iOS で Playwright を使うには BrowserStack などのクラウド実機サービスが現実的な選択肢になる。

### Selenium / safaridriver

Apple の `safaridriver` は WebDriver で Safari を自動化でき、iOS / iPadOS Safari も connected Mac 経由で対象にできる。Safari 側の Remote Automation / WebDriver 有効化が必要で、通常の browsing state とは分離された automation session になる。

これは「実機 Safari を WebDriver で動かす」正攻法だが、Kozaneba の既存 Cypress test をそのまま流用するものではない。Selenium/WebDriver 用に smoke test を別実装する必要がある。

### Appium

Appium XCUITest driver は iOS 実機と Safari / webview 自動化に対応する。Safari を対象にする場合は `browserName: Safari` を使う。実機では Apple の制約により setup が重く、WebDriverAgent、Xcode signing、device trust、Web Inspector / Remote Automation 設定などが絡む。

Kozaneba で自前実機自動テストを作るなら、Appium + WebdriverIO または Appium + Selenium が本命。ただし導入コストと flaky さを考えると、最初は小さな smoke test だけに限定するのがよい。

### クラウド実機サービス

BrowserStack などは real iOS device 上の Safari automation を提供している。BrowserStack は Playwright tests on real iOS devices も提供しており、既存 Playwright script をクラウド実機に投げる経路がある。

長期的に CI へ iPad 実機 smoke を入れるなら、自前で Mac + iPad + signing を維持するよりクラウド実機サービスの方が運用しやすい可能性が高い。ただし費用、local dev server への tunnel、実行時間、flaky 対応は必要。

## 現実的な段階

Kozaneba では次の 3 段階が現実的。

1. desktop CI: 現行 Cypress / unit / build / preflight で通常 regression を守る。
2. desktop WebKit or Playwright emulation: iPad viewport、`hasTouch`、pointer event regression を自動化する。これは実機ではないが安く回せる。
3. iPad 実機 smoke: まず手動。必要になったら Appium/Selenium か BrowserStack Playwright で、起動、追加、drag、selection、group drop、線、辺ラベル編集だけを自動化する。

完全な iPad 回帰網羅を最初から作るのは費用対効果が低い。Kozaneba の問題候補は pointer / touch / group drop / keyboard viewport に集中しているので、実機自動化もそこだけを狭く切る。

### 1. まず desktop で通常テストを通す

実機に持ち込む前に、対象 branch で以下を通す。

```sh
npm run codex:preflight
```

ここで boot、line label regression、unit tests、production build を確認する。iPad 実機テストは、この通常 gate を置き換えるものではなく、入力イベントと Safari 依存を追加で見る層。

### 2. LAN で iPad から dev server に接続する

現行 `vite.config.ts` は dev server host が `127.0.0.1` 固定なので、そのままでは iPad から見えない。実機確認時は host を上書きする。

```sh
npm start -- --host 0.0.0.0 --port 3000
```

Mac と iPad を同じ Wi-Fi に置き、Mac の LAN IP を調べる。

```sh
ipconfig getifaddr en0
```

iPad Safari で次にアクセスする。

```text
http://<MacのLAN-IP>:3000/#blank
```

Mac firewall が止めている場合は、Node / Vite への着信を許可する。

注意: Google sign-in / Firebase Auth まで見る場合、LAN IP の HTTP origin は Firebase の authorized domain や OAuth redirect の制約に当たりやすい。認証を含む確認は Netlify deploy preview など HTTPS の公開 URL で見る方が現実的。

### 3. 実機 smoke test の最小チェックリスト

最低限、次を iPad の Safari で確認する。

- `#blank` が白画面にならず起動する。
- menu から Kozane を追加できる。
- 既存 Kozane をタップして menu が出る。
- Kozane を指で drag でき、指を離した位置で止まる。
- canvas 空白を drag して選択範囲を作れる。
- 複数 Kozane を選択し、selection menu が出る。
- 選択した Kozane 群を drag できる。
- group 作成、group への drop、group から外への drag ができる。
- nested group で root -> group、group -> root、group -> group の移動後に位置がずれない。
- 線を引く機能で、始点選択、終点選択、線表示ができる。
- 辺ラベルをタップして編集でき、iPad のソフトウェアキーボード表示後も dialog / input が画面外に消えない。
- pinch / browser scroll / long press が canvas 操作を邪魔しない。
- Google sign-in または anonymous save を、確認対象に応じて別途見る。

### 4. Safari Web Inspector で失敗を観測する

実機で「動かない」を再現したら、Mac の Safari から iPad のページを Web Inspector で開き、console error と network failure を見る。Sentry に届く場合は [運用エラー観察](運用エラー観察.md) の分類で、touch / wheel / viewport / Safari 依存として記録する。

観測時に残すとよい情報:

- iPadOS version
- Safari かホーム画面 PWA か
- URL (`#blank`, `#edit=<ba>`, deploy preview など)
- 指 / Pencil / external trackpad / mouse のどれか
- 失敗した最小操作列
- console error / Sentry issue id

## 完了条件

iPad 対応を「動くようになった」と判断するには、desktop CI success だけでは足りない。以下を満たす必要がある。

- desktop の `codex:preflight` が pass。
- iPad Safari の実機 smoke test が pass。
- 少なくとも drag / selection / group drop / line creation / label edit の主要 gesture が指で確認済み。
- 認証と保存を対象に含めるなら、HTTPS deploy preview で sign-in / anonymous save / reload 復元まで確認済み。
- 失敗時に Safari Web Inspector または Sentry で観測できる導線がある。
