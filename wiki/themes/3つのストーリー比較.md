# Kozaneba の次に進む 3 つのストーリー比較

## このページの問い

Kozaneba の長い系譜を踏まえたとき、次の一手は大きく 3 つに見える。

1. **今の Kozaneba を改善し続ける**
2. **Kozaneba に似たものを新しく作る**
3. **Kozaneba とは入口の違う全く新しいものを作る**

本ページではこの 3 案を、歴史との連続性、何を解決し何を切り捨てるか、最小実装(MVP)、どの観察が分岐判断になるか、の観点で比較する。

## まず歴史から見えること

[系譜](系譜.md) と [Kozaneba git history 2025 要約](../sources/kozaneba-git-history-2025.md) を通して見ると、Kozaneba の歴史には一貫した流れがある。

- 2021 前半: **空間操作の基盤づくり**
  - テスト、状態管理、グループ、選択、ズーム、ドラッグ
- 2021 後半: **人に使ってもらうためのプロダクト化**
  - 保存、認証、チュートリアル、フィードバック、監視
- 2021-12 以降: **線の必要性の自覚**
  - 近接だけでは足りず、関係を外に出したい
- 2022-2023: **実運用しながら Scrapbox 連携と操作系を増築**
- 2025: **継続可能性の回復 + 関係表現の再強化**
  - 依存更新、Selection menu 強化、merge の意味変更、線ラベルの試行

つまり歴史的に見ると、Kozaneba はずっと

- 「空間で考える」
- 「まだ言葉になっていない構造を扱う」
- 「近接から関係へ進みたい」

という 3 つの軸を抱え続けている。

したがって次の分岐は、

- **空間 UI を主戦場にし続けるか**
- **その前のデータモデルを作り直すか**
- **そもそもの入口を空間以外へ移すか**

の違いとして考えると整理しやすい。

## 1. 3 案の比較表

| 案 | 一言でいうと | 守るもの | 捨てるもの | 主な解決対象 | 最大のリスク |
|---|---|---|---|---|---|
| **A. 改善** | 現 Kozaneba を磨き続ける | 今の UI、既存データ、作業フロー | 構造的な抜本整理は後回し | 直近の自分の作業速度、辺ラベル、Selection 操作、源の長文 | 現設計の負債を抱えたまま局所最適化になる |
| **B. 似たものを新しく作る** | Kozaneba の本質を保って再実装 | 前言語的構造化、空間思考、関係探索 | 現 UI/データ構造/命名への依存 | Situation→Aspect→Relation→View の素直なデータモデル | 「ただの canvas app」になって独自性を失う |
| **C. 全く新しいもの** | Kozaneba から得た洞察を別入口で実装 | 前言語層の扱い、人間+AI の協働原理 | canvas を主役にする前提 | 対話入口、読書入口、AI 候補生成、専門家支援 | Kozaneba 的な強みが薄まり、普通の AI ツールになる |

## 2. 各案の読み

### A. 今の Kozaneba を改善していくストーリー

これは [3 Plan 議論](3plan議論.md) でいう Plan B を、より明示的な「改善路線」として読むもの。

向いている問い:

- 今の 300 件作業を最短で速くしたいか
- いま困っていることは「入口が違う」より「機能が足りない」か
- 現在のデータや操作習慣を捨てたくないか

この路線で素直に伸ばすべき改善軸:

- **関係表現**
  - 線ラベルを使えるものにする
  - 線を単なる描画ではなく意味オブジェクトとして扱う
- **探索操作**
  - Selection ベース変形をさらに軽くする
  - merge / split / tear を「ねりねり」向けに再設計する
- **Situation 接続**
  - [源の長文](../concepts/源の長文.md) を持てるようにする
  - Scrapbox / 長文 / 読書メモからこざねが生える経路を明示する

この案の強みは、**最短で作業価値が出る**こと。弱みは、現 Kozaneba が持つ「こざね中心・関係後付け」の癖を引きずること。

### B. 新しく似たものを作るストーリー

これは Kozaneba の本質を保ったまま、実装とデータモデルをいったん切る案。見た目は canvas 系に見えるかもしれないが、核心は UI より **データモデルの作り直し** にある。

向いている問い:

- 問題は機能不足ではなく、今のモデルそのものにあるか
- 「源の長文」「関係場」「複数 Story」などを後付けではなく最初から入れたいか
- Kozaneba の強みを残しつつ、古い制約を捨てたいか

最初から入れたい前提:

- 1 つの Situation から N 個の断片が生える
- 断片と関係が同格で、関係にも属性がある
- Story / View が分離され、同じ断片を複数の読み筋で再利用できる
- 「こざねを置く場」より「構造が育つ場」に近い命名と世界観

この案の強みは、**Kozaneba らしさを残したまま構造的負債を切れる**こと。弱みは、継承すべき本質を明確に言語化できないと、ただの別実装に崩れること。

### C. 全く新しいものを作るストーリー

これは Plan A 的な方向を、さらに徹底して「Kozaneba の後継」ではなく別プロダクトとして作る案。入口は空間でなく、対話、読書、選択肢反応、違和感ボタンなどかもしれない。

向いている問い:

- 解くべき問題は空間整理そのものではなく、人がまだ持てていない構造を外に出すことか
- 専門家が最初に触る入口は canvas ではないのではないか
- AI を候補生成役に置く設計の方が本質に近いか

この案で中心になるのは:

- 対話や読書から Situation を引き出す
- AI が構造候補を仮説として出す
- 人間が選び、直し、必要なら空間 view で確認する
- Stories として読み筋や説明責任を立てる

この案の強みは、**Kozaneba の UX 上の重さをいったん捨てられる**こと。弱みは、空間操作の豊かさを失って「ありふれた AI 要約・壁打ちツール」に落ちやすいこと。

## 3. それぞれの MVP

### A 案の MVP: 現 Kozaneba を 300 件作業用に尖らせる

MVP の条件:

- Scrapbox / 長文 / 読書メモから断片を取り込める
- 断片が「どの長文から来たか」を保持できる
- 線に最低限のラベルまたは関係種別を持てる
- Selection 操作で複数断片を軽く変形できる

MVP イメージ:

1. 1 つの文書集合を投入する
2. 断片を並べ替える
3. 線を引き、最低限の関係名をつける
4. 断片をクリックすると元文脈へ戻れる
5. 途中成果を保存・再開できる

成功指標:

- nishio 自身の 300 件作業が実際に速くなる
- 「今はこれで十分」と感じる期間が数週間以上続く

### B 案の MVP: Kozaneba 2 と呼べる最小核

MVP の条件:

- Situation / Aspect / Relation / View を別オブジェクトとして持つ
- 1 長文 → N 断片の経路を保持できる
- 同じ断片を複数 View で使い回せる
- 関係にもラベル、根拠、仮説度を持てる

MVP イメージ:

1. 1 本の長文または 1 小プロジェクトを投入
2. そこから断片を複数切り出す
3. 関係を作る時に、ノード本文ではなく relation 側へ意味を書く
4. 別 view を作って違う構造仮説を並べる
5. ある view から story を 1 本出力する

成功指標:

- 「現 Kozaneba に戻らなくてもよい」と感じる作業が出る
- Story / View 分離の価値が実感できる

### C 案の MVP: 新しい入口を持つ専門家向け道具

MVP の条件:

- 対話または読書を入口にできる
- AI が断片候補・関係候補・問い返しを出せる
- 人間が候補を採否し、自分の構造として確定できる
- 結果は空間 view でも物語 view でも見られる

MVP イメージ:

1. ユーザが文章を入れるか、対話を始める
2. AI が「気になる断片」「曖昧な関係」「言い換え候補」を返す
3. ユーザが違和感や同意で選ぶ
4. システムが暫定構造を作る
5. ユーザが 1 本の説明、地図、論点整理として持ち帰る

成功指標:

- canvas 操作に慣れていない人でも価値に到達できる
- それでも「普通のチャットボットでは得られない構造化」が起きる

## 4. どの観察が出たらどの案へ進むべきか

### A 案へ進むべき観察

- 実際の詰まりが、操作不足や小さな機能欠如に集中している
- `work/kozaneba` を直すだけで作業速度が目に見えて上がる
- 新しいデータモデルがなくても、かなりの作業が前進する
- 今の UI にすでに身体化された強みがある

読み:
根本問題はまだ「設計の限界」ではなく「未実装」。

### B 案へ進むべき観察

- 同じ断片を複数の文脈で使いたい場面が頻発する
- relation を node 本文へ押し込んでいる感覚が強い
- 「元文脈」「断片」「構造仮説」を分けて持ちたくなる
- Kozaneba を直しても、毎回同じ構造負債に戻ってしまう

読み:
問題は UI ではなく **モデルの不足**。

### C 案へ進むべき観察

- 本当に欲しい価値が、空間整理より対話や読書支援で先に出る
- 他人に試してもらうと canvas が初手として重い
- 「どこに置くか」より「何が気になっているか」「どう問い返されるか」の方が効く
- AI の候補生成や違和感対話が、空間操作より価値を出している

読み:
問題はモデルだけでなく **入口設計**。

## 5. 三段構えとしてどう運ぶか

3 案は排他的でなく、時間軸に並べられる。

### 短期

まず A 案で現 Kozaneba を改善し、自分の作業を速くする。これは最も安く、最も多くの観察を生む。

### 中期

A を回しながら、B に必要な観察を集める。

- どこで relation が苦しいか
- どこで source_situation が必要か
- どこで同じ断片を別 view で使いたいか

### 長期

それでもなお「入口の重さ」が消えないなら C に進む。C は B の上に載る可能性もあるし、B を飛ばして別プロダクトになる可能性もある。

## 6. 現時点の暫定見立て

現時点では、最も筋が良いのは次の順番。

1. **A 案を先にやる**
   - 直近価値が最大
   - 歴史的にも、Kozaneba は使いながら次の要求が見えるタイプの道具
2. **B 案を本命候補として育てる**
   - [断片中心から関係中心へ](断片中心から関係中心へ.md) の重心移動
   - [関係を第一級にする](関係を第一級にする.md)
   - [源の長文](../concepts/源の長文.md)
   - これらは現 Kozaneba の局所改善だけでは吸収しにくい
3. **C 案は B の外側にある入口戦略として温存**
   - Plan A を本当に新規サービスにするなら、入口は canvas に限らない

要するに、

- **A** は「今の作業場を磨く」
- **B** は「同じ本質を持つ次の作業場を作る」
- **C** は「その能力を別の入口で社会化する」

という役割分担になる。
