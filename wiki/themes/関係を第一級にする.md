## このテーマの問い

知識管理 UI(マインドマップ、概念マップ、ノートツール、KJ法系ツール、知識グラフ)は歴史的に **ノードを発達させ、エッジを線として劣化表示してきた**。その結果、関係的知識がノード本文に埋もれ、グラフ上では毛玉として現れる。

このテーマは [Kozaneba](../entities/Kozaneba.md) を含む知識 UI 全体への構造的批判として、2026-05 の [raw/a.txt](../../raw/a.txt) で展開された議論を整理する。[断片中心から関係中心へ](断片中心から関係中心へ.md) が nishio 視点の歴史記述だとすれば、本ページは設計論として **何をすべきか** に焦点を当てる。

## 中心命題

> 従来の知識UIは、対象を保存する器としてノードを発達させたが、
> 関係を保存する器としてのエッジを発達させなかった。
> その結果、関係的な知識がノード本文に埋没し、
> グラフ上では単なる線として劣化表示され、毛玉化した。
> ([raw/a.txt](../../raw/a.txt))

これは「リンクラベルを増やせばよい」という浅い話ではなく、**ノード中心主義の批判** である。

## ノードとエッジの非対称性

|  | ノード | エッジ |
|---|---|---|
| 通常の表現力 | タイトル、本文、画像、タグ、コメント、履歴、埋め込み、メタデータ | 線、矢印、ラベル、色、太さ |
| 持てる情報量 | リッチ | 貧しい |

しかし、関係の方がリッチである場面は多い。例:

> 田中は、2023 年の論文で、A が B の原因であると主張した。ただし根拠は実験 C で、後に D によって反証された。

これは A にも B にも自然には収まらない。中心は **A と B の関係についての主張** である。

## 「ノード本文の関係負債」という概念

[raw/a.txt](../../raw/a.txt) で提示された有用なメタファー。**ノード本文に押し込まれているが、本来は関係オブジェクトの属性であるべき情報** を「関係負債」と呼ぶ。

### 関係側に置くべきもの

- 「A は B の原因である」
- 「A は B を支持する」
- 「A は B の例外である」
- 「A と B は同じ構造を持つ」
- 「A は B の翻訳である」
- 「A は B の古い版である」
- 「A は B を C という観点から説明している」
- 「A と B の違いは D である」
- 「A は B に似ているが、E の点では異なる」
- 「A は B を誤解している」
- 「A は B を前提にしている」
- 「A は B を通じて C に接続する」

### ノード側に置くべきもの

- 対象の定義、名称、要約
- 内部構造、代表例、固有属性
- 観察記録、本文、画像、履歴

### 分離基準

> その情報が、対象単体を説明するならノード。
> 複数対象のあいだで成立する主張・条件・差異・変換なら関係。

ただし実際には境界が揺れる。だから LLM 補助が有効になる。

## 関係オブジェクトの属性モデル

関係を第一級にするとき、少なくとも以下を持つ:

```
Relation
- id
- type: supports / contradicts / causes / part-of / cites / transforms / analogous-to ...
- participants:
    - role: source / target / evidence / author / context / exception ...
- anchors: ノード全体ではなく、文書中の特定範囲、図の一部、発言、コード行など
- polarity: 肯定 / 否定 / 条件付き / 保留
- modality: 事実 / 仮説 / 主張 / 比喩 / 設計判断 / 予測
- temporal scope: いつ成立したか、いつまで有効か
- provenance: 誰が作ったか、どの資料に基づくか
- confidence: 確信度、人間承認済みか、LLM 推定か
- visibility: 自分だけ / チーム / 公開
- lifecycle: draft / accepted / disputed / deprecated
```

ノードと関係はどちらも本文、履歴、注釈、出典、状態を持てる。違いは「リッチかどうか」ではなく、**何を中心に束ねているか**:

- ノード = 対象を束ねる
- 関係 = 対象間の成立条件・文脈・主張・変換を束ねる

## 既存系譜

ノード中心主義からの脱却を試みる系譜:

| 系譜 | 何をしているか |
|---|---|
| Open Hypermedia | リンクを文書中の埋め込み命令ではなく、ID と属性を持つ第一級オブジェクトに |
| Wikidata | statement に qualifier、reference、rank を付けて文脈化 |
| RDF 1.2 | triple term で「文について文を述べる」を標準化 |
| W3C N-ary Relations | 二項では表せない関係を関係インスタンス化 |
| IBIS / gIBIS | Issue, Position, Argument という型つき関係を扱う議論支援 |
| Compendium | 議論マッピングの構造化と運用負荷の継続的論点 |
| Unfolding Edges (UCLAB) | エッジ属性を必要時に展開する意味ズーム |
| ハイパーグラフDB研究 | N項事実を二項分解せずに保持 |
| GraphRAG / LLM-empowered KG | 自然文から関係抽出してグラフ構築 |

ただしどれも「日常的な知的作業 UI としての実装」には至っていない。Kozaneba が探索しているのはまさにそこ。

## 保存モデルと表示モデルの分離

「関係をリッチにする」を素朴に実装すると、画面が「線の毛玉」から「カードの毛玉」になる。重要なのは:

**保存モデル**(内部):

```
Relation R {
  participants: [
    {role: source, target: A},
    {role: target, target: B},
    {role: evidence, target: C}
  ]
  ...
}
```

**表示モデル**(用途に応じて切り替え):

```
通常表示: A ─ B
詳細表示: A ─ [R カード] ─ B
表形式:   source | relation | target | evidence | status
議論表示: claim → support / objection / rebuttal
時系列:   relation 成立・変更の履歴
```

## 意味ズーム

[Unfolding Edges](https://uclab.fh-potsdam.de/publications/unfolding-edges-adding-context-to-edges-in) の発想に近い段階的展開:

```
Level 0: 関係の存在だけ        A ─ B
Level 1: 関係型だけ            A ── supports ── B
Level 2: 状態・極性・強度       A ── supports / weak / disputed ── B
Level 3: 関係カード(属性表示)
Level 4: 関係の内部構造(support, caveat, exception, provenance, alternative)
```

普段は Level 0〜1、必要なときだけ Level 3〜4 に展開する。

## LLM の役割

関係を第一級にする上で LLM が果たす役割は、**自動分類器ではない**:

1. **配置差分の提示**: ノード本文に書かれた関係的情報を、どの関係オブジェクトのどの属性に移せるかの差分を提案
2. **持ち上げの補助**: 自然文から複数の側面・関係候補を抽出(決定はしない)
3. **未確定さの保存**: 「どれも違う」「まだ語がない」を許す UI を維持
4. **根拠アンカー**: 推定した関係は必ず元の発話・文にアンカーする

危険な失敗パターン:

- LLM が勝手に再配置する(原文アンカー、差分、代替案、取り消しが必要)
- システム語をユーザに押しつける(「これは構造的写像ですね?」型)

## Kozaneba 設計への含意

[活用されなかった機能](活用されなかった機能.md) で挙げた N項関係 UI・囲んで畳む・辺ラベル無しの線は、すべて **ノード偏重 / 二項投影偏重** の症状と読み替えられる:

- N項関係 UI → 関係をリッチにしようとしたが、UI は「線をリッチにする」止まりだった
- 囲んで畳む → グループ自体を「関係オブジェクト」として扱えていない(物理的な箱としてしか扱わない)
- 辺ラベル無しの線 → 関係オブジェクトの最低限の属性すら持たない

Canvas 化 / 作り直し([Canvas移行の検討](Canvas移行の検討.md))において、これらを **機能としてではなく設計哲学として** 移植先で書き直すべきポイント。

2026-05-16 の [3 Plan 議論](3plan議論.md) で、「移植先」は単なる Canvas 化ではなく **[Keichobot](../entities/Keichobot.md) / [いどばた](../entities/いどばた.md) / Kozaneba を参考にした全く新しいサービス(Plan A)** になることが明確化した。Plan A は本テーマで言語化された設計哲学の直接の実装ターゲットになる:

- ノード偏重 → 関係オブジェクトを第一級に持つデータモデル
- ノード本文の関係負債 → Lift 操作で関係場に持ち上げる UI([Clean Relation Elicitation](Clean_Relation_Elicitation.md))
- 関係の平坦化を避ける設計([llm-wiki / relation-flattening](../../../llm-wiki/wiki/concepts/relation-flattening.md))

Plan A の対話レイヤと併せて、本テーマで言語化された設計哲学が「機能の追加」ではなく「最初から第一級として」実装される初めての機会になる。

2026-05-19 の [3つのストーリー比較](3つのストーリー比較.md) では、このテーマが特に **「似たものを新しく作るストーリー」** の中核に位置づけられた。理由は、現 Kozaneba 改善路線では relation を強くできても、node / relation / source situation / view の分離は後付けになりやすいから。

言い換えると:

- **改善ストーリー**: relation-first 哲学を部分移植する
- **似たもの新規ストーリー**: relation-first 哲学をデータモデルの中核にする
- **全く新しいものストーリー**: relation-first 哲学を対話入口と組み合わせて別プロダクト化する

このため本テーマは、単なる「次に欲しい機能」のメモではなく、どのストーリーが必要かを判定するリトマス紙にもなる。
