## このテーマの問い

[Kozaneba](../entities/Kozaneba.md) は現状、**「場 = 1 個の巨大 JSON ドキュメント」** で永続化している([kozaneba-code-architecture.md](../sources/kozaneba-code-architecture.md))。`itemStore / drawOrder / annotations / scale / trans_*` を 1 つの Firestore ドキュメントに詰め、`setGlobal` で全部メモリに載せる。

nishio による観察(2026-06-01):

> 1000〜2000 こざねが限界だからまあいいかと思っていたが、Scrapbox などの長文をこざねとすることの妨げになっている。

つまり「こざねの数」よりも先に **「1 こざねが持てる本文サイズ」** がボトルネックを規定している。1 巨大 JSON だと長文を入れると即座に Firestore の 1MB ドキュメント上限と物理演算の O(N²) スケーリングを両方押しつぶす([物理演算](../concepts/物理演算.md))。

[源の長文](../concepts/源の長文.md) を一級データにする要求とも同じ場所で衝突する: 源の長文を入れる場所がそもそもない。

## 現状スキーマ(再掲)

| Item type | 主なフィールド | 長文への対応 |
|---|---|---|
| `kozane` | `text`, `position`, `scale`, `custom.{ style?, url? }` | 短いテキストのみ |
| `group` | `text`, `position`, `items: TItemId[]`, `isOpen`, `scale` | 表札テキストのみ |
| `scrapbox` | `text`, `image`, `url`, `description: string[]`, `position`, `scale` | URL 経由の間接参照のみ |
| `gyazo` | `url`, `text`, `position`, `scale` | n/a |

長文を持てる Item type がない。`scrapbox` の `description: string[]` は本文要約のキャッシュであって、源の長文そのものではない。

## 2025-26 の外側を見る

巨大 JSON 問題を解いている系統は大きく 4 つ。

### A. CRDT + subdocuments(Yjs / Automerge / Loro)

**[Yjs](https://docs.yjs.dev/api/subdocuments)** は `Y.Doc` の子に subdocument を持てる。「場 = 親 Doc(配置・参照・線)」「こざね本文 = 子 Doc」とすれば、子は `.load()` するまで空のまま転送されない。永続化は `y-indexeddb`、サーバは [Hocuspocus](https://github.com/ueberdosis/hocuspocus) / y-redis / [Liveblocks](https://liveblocks.io/docs/guides/yjs-best-practices-and-tips) / y-partykit。ただし **Yjs コミュニティは「subdocuments は最後の手段」と公式に言っている**(provider 実装と awareness 分離が複雑になる)。1 doc あたり 1〜数 MB が経験則の上限、それを超えるなら subdoc 検討、という肌感が discussion thread に残っている。

**[Automerge 3.0](https://automerge.org/blog/automerge-3/)**(2025)は 2 系比でメモリ約 10 倍削減(Moby Dick で 700MB → 1.3MB)、ロード時間も「17 時間かかっていた文書が 9 秒」レベル。**Automerge Repo** は doc を URL(`automerge:<base58>`)で参照する仕組みで、内部ストレージは **content-addressed**(`chunk_id = ハッシュ`)。「複数 doc を repo に並べて `useDocument(url)` で必要なときに開く」運用が素直で、subdocs ほどの複雑さを抱え込まない。

**[Loro](https://www.loro.dev/docs/tutorial/tree)**(2024-25 新興、Rust+WASM)が一番 Kozaneba と噛み合う可能性がある。**Movable Tree CRDT**(Kleppmann アルゴリズム + fractional index)を一級で持ち、これは「こざねをグループに入れる/出す/別グループへ移す」操作そのもの。さらに **Shallow snapshot**(指定バージョン以前を捨てて履歴を切れる)、**Ephemeral Store**(履歴を持たない LWW、presence 用)で、Kozaneba の [ねりねり](../concepts/ねりねり.md) の歴史を選択的に残せる。公称 360,000 op の doc を 8.4MB メモリ / 361KB ストレージで保持。

### B. クエリベース sync engine(Replicache → Zero / Triplit / ElectricSQL / PowerSync)

「全部メモリ前提」を捨て、ブラウザ内に SQLite / KV を置き、**クエリ単位でリアクティブに同期** する系統。

- **[Zero (Rocicorp)](https://zero.rocicorp.dev/)**(2024-25、Replicache の後継):**ZQL** で書いたクエリ結果が常に最新に追随。サーバは Postgres logical replication 購読。「視界内のこざね + その源の長文」のような動的部分同期がクエリ表現できる。Beta は 2025 末〜2026 初頭。**Postgres 必須なので Firestore とは併存できない**。
- **[Triplit 1.0](https://www.triplit.dev/blog/triplit-1.0)**(2025-03):JS フルスタック DB、WebSocket 同期、permission を query filter として宣言する設計。
- **[ElectricSQL 1.x](https://electric-sql.com/blog/2025/03/17/electricsql-1.0-released)**:2024 に方向転換、**「Postgres から Shape(行のサブセット)を HTTP で片方向 sync」する replication layer に絞った**。SQLite への流し込みは公式責務ではなくなった。
- **[PowerSync](https://www.powersync.com/blog/powersync-2025-roadmap-sqlite-web-speed-and-versatility)**:Postgres/MongoDB/MySQL ↔ SQLite 双方向、Sync Streams で動的部分同期。

この系統は強力だが、Kozaneba にとっては **Firestore を捨てる決断とセット** になる。Plan A の新規サービスなら現実的、Plan B の既存改造には重い。

### C. ブラウザ内 DB(SQLite WASM / libSQL / Turso / PGlite)

クライアント側に本格 DB を持ち、巨大データを scalable に扱う。

- **[SQLite WASM + OPFS](https://github.com/asg017/sqlite-vec)** + **[SQLocal](https://sqlocal.dev/)** ラッパー: 数百万行が現実的。**FTS5 で全文検索**、**`sqlite-vec`**(2024-08、純 C、WASM ビルド ~5.9MB)で **ブラウザ内ベクトル検索**。源の長文の意味的近似検索が手元で可能。
- **[libSQL / Turso](https://turso.tech/blog/local-first-cloud-connected-sqlite-with-turso-embedded-replicas)**: **embedded replica**(ローカル SQLite ファイルがリモートと同期、読み即時 / 書き push)が核。Turso 自体は SQLite を Rust で書き直した別実装に進化中、`@tursodatabase/sync-wasm` で OPFS+WASM 同期を公称。
- **[PGlite](https://pglite.dev/)**: Postgres を WASM 化した 3MB ライブラリ。pgvector / PostGIS 等の拡張がブラウザで動く。

物理演算の [O(N²) 問題](../concepts/物理演算.md) を「視界内ペアだけ」に縮退するにも、空間 index(R-tree、rbush)を SQLite 側に持つのが筋。

### D. Content-addressable blob 層(Iroh-blobs / Patchwork 系 / Roam block ref)

[源の長文](../concepts/源の長文.md) を「**SHA-256 / BLAKE3 ハッシュで識別される blob**」として CRDT/DB の外に置き、こざねは `{hash, anchor_start, anchor_end}` だけを持つ二層構造。

- **[Iroh-blobs](https://docs.iroh.computer/protocols/blobs)** v0.95(2025-10): BLAKE3 で content-addressed、TB 級 blob、verified streaming。
- **[Patchwork](https://www.inkandswitch.com/project/patchwork/)**(Ink & Switch 2024 研究): Automerge 上に作る作家・開発者向けバージョン管理。長文 + diff の UX 研究。
- **Roam の block reference** (`((6064f6c6-...))`):UUID で段落単位を transclude。ただし **UUID は永続 ID であって content hash ではない**(identity-addressing)。同じ内容を別々に書くと別 ID になる。
- **Logseq block ref**:同様に identity-addressing。

「**同じ長文が複数のこざね・複数の場から自動で重複なく参照される**」を実現するには **content-addressing が必要**。identity-addressing(UUID)は重複検出を別途やる必要がある。

## 比較表

| 系統 | 「場 = 1 doc + こざね = 子 / 長文 = blob」の自然さ | Firestore との段階移行 | 物理演算 O(N²) への寄与 |
|---|---|---|---|
| Yjs + subdocs | ◯(設計可、公式は推奨弱め) | ◎ binary update を Firestore に保存する provider 自作で可 | 補助なし(別途空間 index 必要) |
| Automerge 3 + Repo | ◯(URL 参照で複数 doc) | ◎ adapter 自作で可 | 補助なし |
| **Loro** | **◎ Movable Tree が一級** | ◎ adapter 自作で可 | 補助なし |
| Zero | × row 単位、doc 単位ではない | × Postgres 必須、フルリプレース | クエリで viewport 絞れる |
| Triplit / ElectricSQL / PowerSync | × フルリプレース | × | クエリで絞れる |
| SQLite WASM + sqlite-vec | △ DB を設計し直し | △ Firestore は薄い同期層に転落 | ◎ R-tree / FTS5 / vec |
| Iroh-blobs / 自前 CAS | n/a(補助層) | ◎ Firestore Storage で代替可 | 関係なし(長文の重複解消が目的) |

## Kozaneba への含意

### 推奨1: 段階移行ルート(Plan B 寄り)

Firestore を捨てずに、二層分離:

- **(a) 場の構造データ**(配置・グループ・参照・線)を **Loro doc** に置く。binary を Firestore document に保存する provider を自作(Yjs コミュニティに先例多数、同様に書ける)。Loro の Movable Tree は Kozaneba の group 操作と Item の親子変更にそのまま対応。
- **(b) こざね本文 / 源の長文**を **content-addressed blob** として **Firebase Storage** に置く(キー = SHA-256)。こざねは `{hash, anchor?}` だけを保持。

これなら現サーバ・認証・課金を変えずに「巨大 JSON 」「長文の重複」「源の長文の欠落」を同時に解ける。Plan A の検証も兼ねる([3 Plan 議論](3plan議論.md))。

Yjs 選択肢の留保: コミュニティ自身が subdocs を慎重に扱えと言っており、Loro の Movable Tree の方が Kozaneba のドメインに直接効くため、新規採用なら Loro 推し。既に Yjs 知見があるなら Yjs + subdocs でも到達可能。

### 推奨2: 全面書き直しルート(Plan A 寄り)

新規サービスなら **Loro + 自前 CAS + SQLite WASM** の組合せ:

- Loro doc を場の構造として持つ
- SQLite WASM(SQLocal、OPFS、FTS5、sqlite-vec)に「全こざね index」を持ち、viewport / 全文 / 類似検索を高速化
- 長文 blob は S3 互換ストレージか Iroh-blobs に CAS で配置
- サーバ側は Loro の WebSocket sync + blob ストア、認証は別系統

この構成は [関係場](../concepts/関係場.md) / [Clean Relation Elicitation](Clean_Relation_Elicitation.md) のような「関係を第一級にする」設計とも噛み合う(関係場カードも CRDT doc として独立に持てる)。

### Content-addressing の含意

長文を SHA で参照する設計は **思想的にも面白い**:

- 同じ書籍の同じ段落から、別々の場・別々のセッションで生まれたこざねが、自動的に **「同じ源を共有している」と検知** できる
- これは Andy Matuschak の literature note / evergreen note の関係を物理層で実装する形
- [Plurality](../concepts/Plurality.md) / [広聴AI](../concepts/広聴AI.md) のように「複数の人が同じ source 文書からこざねを生やす」ユースケースに自然に拡張できる
- 一方で、長文を編集すると hash が変わるので「変更追跡」を別途設計する必要がある(Patchwork が研究している領域)

## 物理演算スケーリングの位置

データモデルを刷新しても、現状の `ItemRepulse`(全 Item ペアの O(N²) 走査)はそのままでは大規模化で破綻する([物理演算](../concepts/物理演算.md))。データ層に SQLite/R-tree を入れる選択肢(C)は、物理演算側も「視界内 + 近接ペアのみ」に縮退できる **副次効果** がある。データ層と物理層を同じ index で共有できる設計は Loro 単独より一歩進んだ統合。

## Loro のホスティング選択肢(2026-06)

Loro 採用を決めても、**Yjs における Liveblocks / Hocuspocus / y-sweet 相当の公式マネージドサービスは 2026-06 時点で存在しない**。エコシステム規模も Yjs と 2 桁差(週ダウンロード 920K vs 12K、GitHub スター 3.8K)。代わりに 2025 後半に **[Loro Protocol](https://loro.dev/blog/loro-protocol)** が公開され、参照実装(Node の `SimpleServer` と Rust 版 + SQLite 永続化)+ コミュニティ実装が増えた段階。

Kozaneba 文脈での 3 ルート:

### ルート A. Firestore を残し、中身だけ Loro binary 化(移行コスト最小)

- `doc.export({ mode: "snapshot" })` の `Uint8Array` を Firestore document に bytea(base64)で保存
- 差分は `doc.export({ mode: "update", from: vv })` を append-only サブコレクションに積み、定期的に snapshot へ圧縮
- 認証・課金そのまま、サーバ実装ゼロ
- **欠点**: Loro Protocol の ephemeral channel / E2EE / multi-room 多重化 が使えない。presence は Firestore リアルタイムリスナ依存
- **Plan B 段階移行案の最小実装ルート**

### ルート B. Cloudflare Durable Objects + R2(中間コスト・将来性◎)

- DO 1 個 = 場 1 個、in-memory に LoroDoc を持つ
- snapshot は R2 へ、op log は DO storage / D1
- PartyKit の bring-your-own-CRDT 設計 + Loro Protocol の WebSocket frame 転送で ~200-300 行のルーム実装
- **欠点**: Loro 公式 PartyKit テンプレートは存在しない、`loro-crdt` WASM の cold start サイズ、adapter は全自作
- WebSocket 1 接続で多ルーム多重化 + E2EE + ephemeral cursor を含む Loro Protocol の旨味を全部使える

### ルート C. 自前 Node / Rust sync server を Fly.io / Railway へ(運用負荷中)

- **[`@loro-extended/repo`](https://github.com/schoolAI/loro-extended)**(SchoolAI、サードパーティだが最も成熟、`automerge-repo` 思想)+ Hono + Postgres / Supabase
- Storage / Network adapter を差し替える設計、Postgres adapter 既存(LevelDB / IndexedDB も)
- Yjs における Hocuspocus + Postgres パターンの Loro 版
- 1 リージョン運用なら Kozaneba 規模には過剰なほどスケール

### その他の参考実装

- **[loro-dev/protocol](https://github.com/loro-dev/protocol)** SimpleServer (Node、`authenticate` / `onLoadDocument` / `onSaveDocument` フック) と Rust 版 + SQLite
- **[loro-dev/iroh-loro](https://github.com/loro-dev/iroh-loro)**: p2p、iroh-blobs と組合せ(2 peer demo)
- **[typeonce-dev/sync-engine-web](https://github.com/typeonce-dev/sync-engine-web)**: React + TanStack + Web Worker + Effect、教材寄り
- **Liveblocks / Hocuspocus は Loro 非対応**(Yjs 専用 / 独自 data model)、ロードマップ公表もなし

### 比較表

| ルート | persistence | 移行コスト | 将来性 | Kozaneba 適合度 |
|---|---|---|---|---|
| A. Firestore + Loro binary | Firestore bytea | **最小** | △ | Plan B 即着手可 |
| B. Cloudflare DO + R2 | R2 snapshot + DO/D1 op log | 中 | **◎** | Plan A or 後段 |
| C. 自前 Node/Rust + Postgres | Postgres / SQLite | 中〜大 | ◯ | Plan A 寄り |
| Loro Protocol SimpleServer 単独 | フックに自前実装 | 中 | △ | PoC 向き |

### 総合判断

- **短期(数ヶ月)**: A。Firestore 残しで Loro Movable Tree の旨味だけ取る
- **中期(共同編集に踏み込む)**: B。Cloudflare DO + R2、Loro Protocol の機能を全部使う
- **長期(Firebase を離れる)**: C。`@loro-extended/repo` + Postgres

Loro エコシステム未成熟が最大のリスクで、「既製品」を期待するなら現時点では **Yjs + Liveblocks / Hocuspocus** の方が楽([Yjs vs Automerge vs Loro 2026 比較](https://www.pkgpulse.com/guides/yjs-vs-automerge-vs-loro-crdt-libraries-2026))。一方で Loro Movable Tree が Kozaneba ドメインに直撃する優位はトレードオフに値する。

## 開いた問い

- ルート A(Firestore + Loro binary)の provider 実装を Devin に投げる規模感は数百行程度
- 既存 1MB doc から Loro doc への migration スクリプトは E2E でドッグフーディングできるか
- 長文 blob を **CAS にした瞬間に Firestore Security Rules が成立しなくなる**(blob 単位の権限制御が別系統になる)。Storage rules で「ハッシュを知っている人だけ読める」モデルが許容できるか
- [Scrapboxこざね](../concepts/Scrapboxこざね.md) との二重化: Scrapbox ページ本文を「長文 blob」として取り込むパイプラインは作るのか、URL 参照のままにするのか
