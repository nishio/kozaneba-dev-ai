## このテーマの問い

[関係を第一級にする](関係を第一級にする.md) で「関係オブジェクトをリッチにすべき」と言っても、ユーザに「N項関係を作って」「relation_type を選んで」と命令させると、思考の初期段階(まだ何が項で何が関係か未確定の段階)で硬い構造を強制してしまう。

別の方向として、2026-05 の [raw/a.txt](../../raw/a.txt) Round 4 で nishio が提案したのが:

> 人間が「操作」を自然言語で伝えるのではなく質問への回答とかボタンの操作で少しずつ表出する

これは LLM 時代の「自然言語コマンド UI」とも、従来の「ダイアログでフォーム入力」とも違う **第三の道**:**Clean Relation Elicitation(クリーンな問いによる関係場の漸進的外化)**。

## クリーンランゲージとの整合

[クリーンランゲージ](../concepts/クリーンランゲージ.md)(David Grove)は、相手自身の言葉を使い、自分の解釈語を持ち込まずに質問する技法。これを UI に移すと:

- UI は「関係型を選べ」と言わない
- UI は **ユーザ自身の言葉を使って、注意を向ける問い** を出す
- ユーザの短い回答、選択、保留、違和感表明が、少しずつ [関係場](../concepts/関係場.md) を作る
- ボタンは「命令」ではなく **注意の向け先を選ぶ小さな応答**

## 2種類のボタン

### 注意誘導ボタン(クリーン質問対応)

| クリーン質問の型 | UI ボタン | 内部処理 |
|---|---|---|
| X について他に何がある? | `[もっと]` | X に追加の側面をぶら下げる |
| X はどんな X? | `[性質を探る]` | 側面候補を作る |
| X はどこにある? | `[場所/範囲]` | 文書内位置、概念空間上の位置を保持 |
| X は何に似ている? | `[比喩]` | メタファー候補を作る |
| X と Y に関係はある? | `[関係を見る]` | 関係場のプレースホルダを作る |
| X の直前は? | `[前]` | 時系列・生成過程 |
| X の次は? | `[次]` | 変化・展開 |
| X はどこから来る? | `[由来]` | 根拠、出典、発生源 |
| X には何が必要? | `[必要条件]` | 条件・制約 |

ボタン名が `causes` `supports` `contradicts` のようなオントロジー語ではない点が要。これらはシステム側の推定語であり、最初からユーザに押しつけない。

### フィット確認ボタン(フォーカシング対応)

```
[合う] [近い] [少し違う] [違う]
[強すぎる] [弱すぎる]
[まだ言えない] [保留]
```

これは [Gendlin](../entities/Gendlin.md) の [フェルトセンス](../concepts/フェルトセンス.md) を保存するためのもの。一見「何も操作していない」ように見えるが、関係場の状態(未確定性・語の不足・候補の合わなさ)を更新する重要な操作。

## 中心UI構成: 4パネル

[raw/a.txt](../../raw/a.txt) で提案された構成:

```
┌──────────────────────────────────────────────┐
│  A. Situation Pad                              │
│  原文・メモ・会話・図・違和感・未整理の断片        │
├──────────────────────┬───────────────────────┤
│  B. Aspect Tray       │  C. Relation Field     │
│  持ち上げられた側面     │  N項関係カード群          │
├──────────────────────┴───────────────────────┤
│  D. Projection View                           │
│  線 / 表 / 議論マップ / タイムライン / 文章        │
└──────────────────────────────────────────────┘
```

### A. Situation Pad

ユーザが自然に書く場所。システムは勝手に確定構造へ変換しない。文章中に薄いマーカーを出して「ここから側面を持ち上げる?」と示唆する程度。

### B. Aspect Tray

「この状況から何が持ち上がってきたか」を置く一時保管場所。タグ一覧ではなく、まだノードでもエッジでもない **側面候補** を保持。

```
[類似] [差異軸: 制度/認知] [媒介: C] [反転: D]
[仮説] [まだ語がない] [説明相手に依存] [後で再検討]
```

### C. Relation Field Ledger

複数の応答が集まると、システムが関係場候補を作る:

```
Relation Field Candidate R1
元の言葉: A と B は似ている / 単なる類似ではない / C を通すと対応が見える / D では逆
関与しているもの: A, B, C, D
側面: 類似 / 類似ではない / 媒介 / 対応 / 反転
現在の言い方: C を通すと A と B が対応するが、D では逆になる
状態: 未確定
```

### D. Projection View

関係場の表示形態を切り替える: 線、表、カード、議論マップ、タイムライン、文章。グラフは射影の一つに過ぎず、主画面ではない。

## 操作体系: 5種類

[raw/a.txt](../../raw/a.txt) で提示された関係に関する基本操作:

1. **Lift**: 原文から側面を持ち上げる
2. **Gather**: 複数対象を関係場に集める(まだ relation type は決めない)
3. **Formulate**: 言い方を試す(複数候補、ユーザは「近い」「違う」「保留」)
4. **Project**: 表示を変える(線・表・カード・議論マップ・文章)
5. **Carry forward**: 前の言い方を保ったまま更新する(編集履歴ではなく思考の発展履歴)

## ユーザ語とシステム語を混ぜない

UI が「クリーン」であるために重要なのは、**語の出所を分けて保存する** こと。

```
ユーザの言葉:
  「似ている」「単なる類似ではない」「Cを通すと」「Dでは逆」

システム候補:
  mediated correspondence / inversion / analogy with caveat / structural mapping
```

悪い UI:
```
A と B は「構造的写像」ですね?  [はい] [いいえ]
```

よい UI:
```
あなたの言葉: 「Cを通すと対応する感じ」
近いかもしれない候補:
  [対応] [写像] [媒介] [反転を含む対応] [どれも違う]
```

`[どれも違う]` を選べることが重要。これがないとユーザの未分節な感覚を消してしまう。

## LLM の役割: 質問者と記録係の中間

LLM は二つの役割を持つ:

1. **次に出す問いを選ぶ**: 「今は『何に似ている?』より『X と Y のあいだに関係はある?』の方がよさそう」
2. **回答列から構造候補を作る**: 「これまでの回答から見ると、A, B, C, D を含む関係場候補がある。ただし C が『媒介』なのか『レンズ』なのかは未確定」

LLM 制約:

- ユーザの語を優先する
- 新しい意味語を出すときは「候補」と明示する
- ユーザ語とシステム語を混ぜない
- 推定した関係は根拠となる発話にアンカーする
- 「どれも違う」「まだ」を常に許す
- 自動変更ではなく差分提示にする

## クリーンさの監査

UI 上で各質問に「語の出所」を表示できる:

```
質問: 「Cを通す」とき、A と B に何が起きますか?
語の出所:
  Cを通す: ユーザ
  A: ユーザ
  B: ユーザ
  何が起きる: 質問テンプレート
```

これにより、LLM が知らず知らず「システム語の押しつけ」をしていないか可視化できる。

## 失敗しやすい設計

- いきなり厳密なオントロジー(`relation_type を選んでください: causes / supports / contradicts / ...`)→ 「まだ語がない」が消える
- ボタンが概念分類(`[原因] [根拠] [反例] [媒介] [包含] [類推]`)→ ユーザの中でまだ未確定なものを先に分類してしまう
- グラフビューを主画面にする → 「ノードと線」へ思考が寄る
- LLM が勝手に再配置・要約・命名する → クリーンでなくなる

## Kozaneba / Keichobot との関係

このアイデアは Kozaneba と [Keichobot](../entities/Keichobot.md) の長年の分業構想を再定義する。

### 従来の分業

- [Keichobot](../entities/Keichobot.md) は **モヤモヤ → 言葉** の局面([言語化](../concepts/一次元化.md) と対比)
- [Kozaneba](../entities/Kozaneba.md) は **関係のネットワーク → 一次元化されたストーリー** の局面

cf. [Kozaneba vs Keichobot](Kozaneba_vs_Keichobot.md)

### Clean Relation Elicitation での再定義

両者は連続体になる:

```
未分節な状況
   ↓ [Keichobot / クリーンランゲージ的問い]
側面の持ち上げ
   ↓ [Clean Relation Elicitation 中核]
関係場の漸進的外化
   ↓ [Kozaneba 的射影]
線・表・カード・文章
```

Keichobot は「Situation Pad に書ける材料」を作り、Kozaneba は「関係場を射影として見せる」道具。両者の中間に **Clean Question Deck + Relation Field Ledger** という新しい層が立ち上がる。

これは [いどばた](../entities/いどばた.md) → 概念マップ → Kozaneba / Miro のパイプライン([いどばた/Keichobot→概念マップ→Kozaneba/Miro](../../raw/scrapbox_kozaneba/2025-11-14__いどばた_Keichobot→概念マップ→Kozaneba_Miro.md))とも整合するが、より低レベルの操作単位(「質問への小さな応答」)で構成されている点が違う。

## 評価基準

このUIが機能しているかは次で測れる:

1. ノード本文に埋もれた関係文が減ったか
2. 関係場を検索・再利用できるか
3. 二項リンクに分解せず N項関係を保持できるか
4. **「まだ語がない」を保存できるか**
5. **後から見たとき、思考の進み方が分かるか**
6. グラフ表示が毛玉になっても、表・カード・文章で扱えるか
7. LLM 提案の根拠と差分を確認できるか

特に 4 と 5 が、既存の知識管理 UI が弱い点。
