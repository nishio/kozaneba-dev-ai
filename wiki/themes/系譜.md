## 系譜

```
紙の KJ法/こざね法(2014 頃〜)
   ↓ 不便を電子化
grouping
   ↓
[Regroup](../entities/Regroup.md)
   ↓ 試行錯誤で複雑化、ゼロから書き直し
[Movidea](../entities/Movidea.md)
   ↓ 2021-08-06 にリネーム
[Kozaneba](../entities/Kozaneba.md)(2021-08〜現在)
   ↓ 構想中
Canvas 実装の Kozaneba(2025-08〜検討中)
   ↓ 2026-05-16 の分岐(両方を並行)
Plan B(現Kozaneba改造 + [源の長文](../concepts/源の長文.md) データモデル) + Plan A(全く新しいサービス)
```

Plan A は [Keichobot](../entities/Keichobot.md) / [いどばた](../entities/いどばた.md) / Kozaneba の **3 系列を吸収する合流点** として位置するため、上図の単線上ではなく、Keichobot/いどばた からの流れと合流する形になる。

## 各世代の特徴

### 紙 (2014 頃〜)

- 物理的な紙とペンの KJ法 / [こざね法](../concepts/こざね法.md) を実践
- 数百枚で限界
- 後から動かしにくい(=線が引きにくい)、保存と複製が困難

### grouping

- 最初期版。ソースに技術的詳細はほぼ残っていない

### [Regroup](../entities/Regroup.md)

- 「情報断片を動かしながら頭を整理するプロセスを電子的に支援する」
- 試行錯誤しながら作ったためコード複雑化、テストコードなし
- 新規ユーザのフローが複雑、解説が長くなる

### [Movidea](../entities/Movidea.md)

- Regroup をゼロから書き直し
- Cypress + React-N でテスト可能化
- immer で状態更新可能化(前バージョンで難しかった仕様があっさり実装できた)
- Firebase Auth / Firestore も Cypress でテスト
- 2021-08-06 に Kozaneba にリネーム

### [Kozaneba](../entities/Kozaneba.md)(2021-08〜)

- チュートリアル付き
- [Scrapboxこざね](../concepts/Scrapboxこざね.md) の発明(2021-08〜)
- [線を引く機能](../concepts/線を引く機能.md) 追加(2021-12 までに「必要不可欠」と判定)
- グループ畳み、サイズで重要度表現
- 2023 年: [Devin](../entities/Devin.md) ではない普通の開発再開([Kozanebaの開発環境を作る](../../raw/scrapbox_kozaneba/2023-01-11__Kozanebaの開発環境を作る.md))
- 2024 年: コードを丸ごと o1 Pro に入れて改善点を分析([Kozanebaのコードを丸ごとo1_Proに入れる](../../raw/scrapbox_kozaneba/2024-12-14__Kozanebaのコードを丸ごとo1_Proに入れる.md))
- 2025 年: [Devin](../entities/Devin.md) を投入して機能追加(Scale Double、辺ラベルの実装試行など)

### Canvas 実装の検討(2025-08〜)

[pKozaneba2025-08-26~27](../../raw/scrapbox_kozaneba/2025-08-26__pKozaneba2025-08-26~27.md):

> Kozaneba を Canvas 実装に変えることを想定した考察。基本的にほとんど作り直しだよね。

ボトルネック分析:

- データを 1 つの JSON で Firebase に保存しており 2000 枚程度でサイズの限界
- 1000 件ですらテキストが豆粒になる ([毛玉問題](../concepts/毛玉問題.md) 系)
- 単純にサイズ上限をクリアしてレンダリングエンジンを変えて 10000 件表示してもユーザ価値はない

WebGPU の検討([pKozaneba2025-08-14](../../raw/scrapbox_kozaneba/2025-09-11__pKozaneba2025-08-14.md)): [Devin](../entities/Devin.md) は推奨しない。WebGL も React/DOM の書き換えが大きく推奨しない。Canvas (konva.js など) なら 20000 枚も可能と GPT-5 が主張するが、Devin に「嘘だろ」と詰められる。

→ **広聴 AI 的なもののリーフノード(10000 件以上)**と **1000 件未満で構造化していく Kozaneba** は、無闇に同一視しない方が良いと nishio。

### 2026-05-16: Plan B + Plan A への分岐

[3 Plan 議論](3plan議論.md) で「Kozaneba を改善するか作り直すか」の長年の二項対立が **「両方を時間軸で並行」** に解体された:

- **Plan B**: 現 Kozaneba を改造して nishio 自身の 300 件作業を加速。[源の長文](../concepts/源の長文.md) データモデル拡張を含む。Canvas 化 vs 現 DOM のままで済ますかは Plan B 期間で再評価
- **Plan A**: [Keichobot](../entities/Keichobot.md) / [いどばた](../entities/いどばた.md) / Kozaneba を参考にした **全く新しいサービス**。系譜の直接の延長ではなく、3 つを統合する位置に立つ

系譜上、Plan A は Kozaneba の継承ではなく **分岐**(あるいは 3 系列を吸収する合流点)になりうる。長年の Canvas 移行論([Canvas移行の検討](Canvas移行の検討.md))は Plan A の登場で問いの形が変わった(現 Kozaneba を Canvas 化する必然性は弱まる)。

## コードベースの構成(2024-12 時点の o1 Pro 整理)

[Kozanebaのコードを丸ごとo1_Proに入れる](../../raw/scrapbox_kozaneba/2024-12-14__Kozanebaのコードを丸ごとo1_Proに入れる.md):

- React + TypeScript の Web アプリ
- 状態管理は `reactn`
- URL ハッシュによるモード分岐(new, edit, view, blank, tinysample)
- Firebase (Auth, Firestore) で同期。匿名/Google 認証
- Sentry, Google Analytics

潜在的改善点:

- UserScript の eval(セキュリティ)
- Firestore エラーハンドリング不足
- イベントリスナー解除確認
- グローバル状態のレンダリングコスト
- onWheel での頻発 update
- スタイル混在
- クリップボード操作のエラー処理
