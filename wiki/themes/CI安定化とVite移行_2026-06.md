# CI安定化とVite移行 2026-06

## 位置づけ

[テスト改善計画](テスト改善計画.md) で決めた 3 段階、つまり「座標ロジック単体テストに nested drag の知見を入れる」「Kozaneba 本体側を required CI にする」「CI gate が安定したら Node / CRA 脱出する」を実際に完了した記録。

重要なのは、Node 更新や Vite 移行を先にやらなかったこと。先に nested drag のバグを state / world 座標の regression に変換し、次に GitHub required CI を安定させ、その後で Node 24 と Vite へ移った。

この順序にしたことで、移行中に出た failure を「既存テストの不安定さ」ではなく「今回の変更で発生した差分」として扱えた。

## 実行した順序

### 1. 座標ロジック単体テスト

PR [#40 Add coordinate logic unit tests](https://github.com/nishio/kozaneba/pull/40) で、nested group drag の修正知見を pure helper と単体テストへ移した。

中心は、画面上の pixel ではなく、親グループ chain の offset、root 座標、group 相対座標、`screen_to_world` / `world_to_screen`、`zoom_around_pointer` の invariant を見ること。

これにより、`A(B(C))` のような構造で起きた座標ずれを、Cypress の見た目依存だけでなく状態ロジック側でも検出できるようになった。

### 2. Kozaneba 本体側 required CI

PR [#41 Add Kozaneba CI workflow](https://github.com/nishio/kozaneba/pull/41) で `.github/workflows/kozaneba-ci.yml` を追加し、main branch protection の required check にした。

required check は次の 2 本。

- `Unit, build, and preflight`
- `Cypress with Firebase emulator`

前者は `npm test`、production build、`codex:preflight` を見る。後者は Firebase emulator smoke と `cypress/e2e/kozaneba/*.cy.ts` を見る。

GitHub Actions 上で Firebase emulator を動かすには Java 21 が必要だった。ローカル Mac の Java が古いことは、CI で `actions/setup-java` により Java 21 を明示すれば blocker ではない。

### 3. Node 24

PR [#42 Use Node 24 for app builds](https://github.com/nishio/kozaneba/pull/42) で Node を 24 に寄せた。

変更点は `.nvmrc`、GitHub Actions、Netlify `NODE_VERSION`、README の整合。CI と Netlify が Node 24 で通ることを確認してから次へ進んだ。

この段階ではまだ CRA / `react-scripts` は残っていた。Node 更新と build tool 移行を同時にやらず、差分の切り分けを保った。

### 4. CRA から Vite へ移行

PR [#43 Migrate app build to Vite](https://github.com/nishio/kozaneba/pull/43) で `react-scripts` を外し、Vite / Vitest に移行した。

主な変更:

- `npm start`: `vite`
- `npm run build`: `tsc --noEmit && vite build`
- `npm test`: `vitest run`
- `vite.config.ts` を追加
- root `index.html` を追加し、CRA の `public/index.html` を削除
- `setupTests.ts` を Vitest 用に変更
- CRA の `/static/js/bundle.js` 前提だった preflight / Cypress boot contract を Vite の `/src/index.tsx` 前提へ更新
- Netlify build command を Vite build に更新

PR 側でも merge 後の main 側でも、required CI と Netlify deploy preview が通った。

### 5. Vite 環境 API と Node types の後処理

PR [#44 Clean up Vite environment usage](https://github.com/nishio/kozaneba/pull/44) で、Vite 移行後に残った小さな不整合を整理した。

- app 側の `process.env.NODE_ENV` を `import.meta.env.DEV` / `import.meta.env.PROD` に変更
- `@types/node` を Node 24 系に更新
- Node 24 types で露出した `NodeJS.Timer` と DOM timer の型差分を `ReturnType<typeof setInterval>` に変更

この PR も required CI / CodeQL / Netlify が通り、main merge 後の CI も success になった。

## 結果

2026-06-03 時点で、`work/kozaneba` の main は `d5757f5`。PR #40〜#45 が入り、post-merge の Kozaneba CI は success。

また、Dependabot の open alert は 0 件になった。以前残っていた alert は `react-scripts > webpack-dev-server` 由来であり、CRA を外すことで根本原因ごと消えた。

現在 CI で守れている範囲:

- Vitest unit tests
- TypeScript type check
- Vite production build
- boot contract を含む `codex:preflight`
- Firebase emulator smoke
- Kozaneba 本体 Cypress suite

一方で、Movidea legacy spec は required gate ではない。これは「通すべきテスト」かどうかを棚卸しする対象であり、現行 Kozaneba の merge gate とは分ける。

## Issue #13 / #4 の完了

Issue [#13 CI/CD パイプラインの構築](https://github.com/nishio/kozaneba/issues/13) は、PR #41〜#44 と main CI success を根拠に完了コメントを付けて close した。

Issue [#4 本番環境のコンソールログ削除](https://github.com/nishio/kozaneba/issues/4) は、PR [#45 Route production console logs through dev logger](https://github.com/nishio/kozaneba/pull/45) で対応し、merge により close された。

PR #45 では、`src/` の runtime `console.log` / `console.time` / `console.timeEnd` を既存の `dev_log` / `dev_time` / `dev_time_end` に寄せた。`console.error` は実エラー報告として残した。`rg` で確認すると、実アプリコードに残る direct `console.log/time` は `src/utils/dev.ts` の wrapper だけになった。

PR #45 は local で `npm test`、`npm run build`、`npm run codex:preflight`、`npm audit --audit-level=moderate` が通り、PR CI / main post-merge CI も success だった。

## 学び

### 1. CI gate を先に安定させると移行が小さくなる

CRA 脱出は大きな作業に見えるが、先に required CI を作っておくと、Vite 移行は「build tool の差分」として扱える。逆に CI がないまま移行すると、既存の Cypress failure、Firebase emulator 不足、Node / Java 不整合、CRA 差分が一度に混ざる。

今回うまくいった理由は、移行前に Kozaneba 本体 Cypress を required CI で通る状態にしていたこと。

### 2. 「なるべく多くを CI で動かす」と「required にする」は別

nishio の指摘どおり、テストは CI 上でなるべく動かすべきである。ただし、それを全部 required gate にする必要はない。

今回 required にしたのは、現行 Kozaneba 本体を壊したら止めるべき subset。Movidea legacy は観測・棚卸し対象として残し、required にはしなかった。この分離により、CI の価値と merge velocity の両方を保てた。

### 3. Firebase emulator は GitHub CI で動く

ローカルの Java が古くても、GitHub Actions で Java 21 を固定すれば `firebase-tools@15` と emulator は動く。これは今後の保存・認証・チュートリアル系テストを CI gate に載せるための重要な確認になった。

### 4. 座標ロジックの unit test は移行の保険になる

Vite 移行そのものは UI の見た目を変える作業ではないが、build tool 更新では timing、module resolution、test runner、dev/prod 分岐が変わる。nested drag のような座標バグを state / world 座標側で固定しておくと、移行後に「見た目がたまたま通る」だけではない安心材料になる。

### 5. 推移依存の alert は、上書きより根本依存を外す方がよいことがある

`webpack-dev-server` alert は override で消そうとすると CRA dev server を壊した。今回は `react-scripts` 自体を外したことで、alert の原因を消せた。

これは「常に migration が正しい」という意味ではない。先に CI gate があったから migration を安全に選べた、という順序の問題である。

### 6. Vite は隠れていた警告を見えるようにした

Vite build では direct `eval` と bundle size warning が出る。これは移行失敗ではないが、CRA 時代には見えにくかった実装上の注意点である。

特に [UserScript](../concepts/UserScript.md) は Kozaneba の機能として intentional にコード実行を持つ。したがって direct `eval` warning は、UserScript の仕様変更としてではなく、既存仕様を維持したまま「意図的なコード実行をどう明示するか」「production console noise や Sentry に混ぜないか」を分ける小さな作業として扱う。

## 次のアクション

優先順位としては、次の順がよい。

1. Vite build warning のうち direct `eval` を整理する。UserScript の仕様は変えず、意図的な `eval` と minifier warning / security warning / Sentry noise を分ける。必要なら、挙動を変えない形で実行境界を明示する。
2. Issue [#17 テストカバレッジの向上](https://github.com/nishio/kozaneba/issues/17) は、広いまま進めず、座標変換・hit test・undo/redo・保存復元などの小さな regression に分解する。同時に旧 Movidea spec を棚卸しし、削除、quarantine、Kozaneba test への統合、unit / integration test への昇格を分類する。
3. Issue [#25 コンポーネントレンダリングのプロファイリング実施](https://github.com/nishio/kozaneba/issues/25) は、Vite build 後に bundle size warning が見えているので、実測の入口として残す。
4. Issue [#12 ブラウザ拡張機能のドキュメント整備](https://github.com/nishio/kozaneba/issues/12) は、ブラウザ拡張を今後も Plan B の対象にするなら README / 導入手順として切る。

2026-06-03 時点で、Kozaneba 側の open Issue は #12 / #17 / #25 の 3 件。#13 と #4 は完了済み。
