# 運用エラー観察

Kozaneba 改善の観測ソースは、Scrapbox の設計メモ、GitHub Issue、Cypress failure、コード読解だけでは足りない。production で実際に起きたエラーを [Sentry](../entities/Sentry.md) から読むことで、ユーザがどこで詰まっているか、どの古い機能がまだ使われているか、どのテストを優先すべきかを判断できる。

## なぜ重要か

Sentry は「実ユーザまたは本番実行で発生した事実」に近い。AI が生成した Issue は提案の束であり、Cypress failure はローカル再現環境の問題と実バグが混ざる。一方で Sentry issue は、少なくとも production に到達したコードパスで何かが壊れたことを示す。

これは [Plan B 試行 2026-06](Plan_B試行_2026-06.md) にとって重要である。現 Kozaneba を改善して自分の作業を加速するなら、想像上の改善よりも、実際に壊れている箇所・実際に使われている導線を先に見るべきだからである。

## ただし直接 backlog にしない

2021-08-16 と 2021-09-09 の開発日記では、ユーザの入力ミス、JSON import の形式エラー、UserScript の試行錯誤は、Sentry に送るのではなくユーザへフィードバックすべきだと整理されていた。

したがって Sentry issue を読むときは、まず次に分類する。

- 本体バグ: 例外として開発者が直すべきもの
- 入力 validation 不足: Sentry ではなく UI feedback に変えるべきもの
- UserScript / 拡張由来: sandbox、try/catch、ユーザ向け error 表示の問題
- 保存・認証・外部サービス: Firebase / Scrapbox / Gyazo / network の失敗
- ブラウザ・端末依存: touch、wheel、viewport、Safari など
- 開発・テストノイズ: production 改善の根拠にしないもの

この分類をしないと、Sentry は「本体バグの観測」ではなく「想定されたユーザ試行錯誤までエラー扱いするノイズ源」になる。

## 観察手順

Sentry にアクセスできるようになったら、まず直近 90 日、必要なら 365 日を見る。

見る項目:

- issue title / stack trace の root frame
- event count / affected users / first seen / last seen
- environment / release / browser / OS
- URL / hash / ba id など、どの画面で起きたか
- Sentry context の `global` が event に付いているか。付いていれば、そこから分かる Kozaneba 状態
- user feedback report dialog の本文
- 既に resolved / ignored になっている issue の再発

記録するときは、個人情報や本文データを wiki に貼らない。保存するのは分類、再現条件の推定、関連コード、次の一手だけでよい。

## Plan B への接続

Sentry から得た issue は、次のように扱う。

1. 上位 issue を 5〜10 件だけ読む。
2. 各 issue を分類し、実装すべきものと UI feedback に変えるべきものを分ける。
3. 本体バグなら `work/kozaneba/` のコードと照合して再現仮説を作る。
4. 再現できるものは unit / Cypress regression に落とす。
5. 再現できないが頻度が高いものは、追加 logging / context を入れる小 PR にする。
6. 判断理由は wiki に残し、実装作業は GitHub Issue または PR に切る。

特に [テスト改善計画](テスト改善計画.md) では、Sentry 上位エラーを required CI の regression 候補として扱う。CI は「理想の網羅」ではなく「実際に壊れたものを二度壊さない」方向から厚くしていく。

## 現時点で分かっていないこと

Sentry の中身はまだ読んでいない。必要なのは Sentry の org / project へのアクセス、または API token / ブラウザログインである。現行コードから分かるのは、production で Sentry が初期化され、DSN project `5898295` に送信されていることまでである。
