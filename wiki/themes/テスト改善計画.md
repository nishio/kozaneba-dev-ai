# テスト改善計画

## 結論

Kozaneba のテスト改善は、次の順序で進める。

1. 座標ロジック単体テストに今回の知見を入れる
2. Kozaneba 本体側を required CI にする
3. CI gate が安定したら Node / CRA 脱出

これは「full Cypress を全部緑にしてから進む」計画ではない。また、Playwright を先に足す計画でもない。まずは Kozaneba 本体の現行挙動を守るために、nested drag 修正で分かった座標バグの型を deterministic な単体・統合テストへ移し、その上で Kozaneba 本体側のテストを required CI にする。

2026-06-03 時点で、この 3 段階は PR #40〜#44 により完了した。実施記録と学びは [CI安定化とVite移行 2026-06](CI安定化とVite移行_2026-06.md) に分けて保存した。

## なぜこの順序か

今回の nested drag 問題は、UI 上では「グループへ出し入れすると座標がずれる」と見えた。しかし原因は pixel rendering ではなく、root 座標と親グループ相対座標の変換、親グループ chain の offset 合計、そして draft state を使った親探索の不整合だった。

したがって、最初に強くするべきなのは screenshot E2E ではなく、state / world 座標のロジックである。ここが薄いまま CI gate だけを required にすると、Cypress の古い DOM 期待値や pixel exact failure と、実装上の本質的な座標バグが混ざってしまう。

## 1. 座標ロジック単体テストに今回の知見を入れる

最初にやることは、nested drag 修正を「Cypress がたまたま通る」状態で終わらせず、座標ロジックの回帰テストとして固定すること。

重点的にテストする知見:

- `get_total_offset_of_parents` は、引数で渡された state に対して `find_parent(current_parent, g)` で親探索しなければならない。
- root から nested group へ入れる branch では、drop 先 group 単体の `position` ではなく、親グループ chain 全体の offset を引く必要がある。
- `A(B(C))` のような nested group で、`C` を root へ出してから再び `B` 配下へ戻しても world 座標が破綻しないことを regression にする。
- canvas drop、group drop、root -> nested、nested -> root、nested -> nested の座標変換を、DOM 座標ではなく `itemStore` 上の state invariant で検査する。
- `screen_to_world` / `world_to_screen` を pure helper として切り出し、相互変換の性質を表形式または property-like test で確認する。
- `zoom_around_pointer` は「cursor 下の world point が zoom 後も同じ」を単体テストで固定する。

この段階での主な正解は、「付箋が画面上のその pixel に見えるか」ではなく、「付箋やグループの world 座標・親子関係・drawOrder が正しいか」に置く。

## 2. Kozaneba 本体側を required CI にする

次に、Kozaneba 本体の現行テストを required CI にする。

PR #39 merge 後の `origin/main` / `work/kozaneba` は `main@c46b5fc` で、nested drag 修正 `5b19a29` を含んでいる。Firebase emulator 付きで Kozaneba 側 Cypress を実行すると、`cypress/e2e/kozaneba/*.cy.ts` は 17 specs / 31 tests が通る状態になった。

required CI に入れる候補:

- `npm test -- --watchAll=false`
- `npm run build`
- `npm run codex:preflight`
- `npm run cypress:emulator-smoke`
- `cypress/e2e/kozaneba/*.cy.ts` 全体を Firebase emulator 付きで走らせる script

この CI を GitHub の required check にする。Kozaneba 本体の boot、build、tutorial、save smoke、drag regression が壊れたときに merge を止めるのが目的である。

GitHub CI で Firebase emulator を動かすこと自体はできる。ただし、現行の `firebase-tools@15` は Java 21 未満を拒否するため、CI runner では `actions/setup-java` などで Java 21+ を明示的に用意する必要がある。Cypress 13.17.0 も binary install / cache を CI に組み込む。

一方で、Movidea legacy はここでは required にしない。

### Sentry から regression 候補を拾う

[運用エラー観察](運用エラー観察.md) で整理したように、Sentry に溜まっている production error は required CI の候補を決める材料になる。

特に上位 issue は、「実際に壊れた導線」として扱う。ただし、JSON import の形式エラーや UserScript の試行錯誤のように、本来はユーザへ feedback すべきものまで regression test にしない。まず本体バグ、入力 validation 不足、UserScript / 拡張由来、保存・認証・外部サービス、ブラウザ依存に分類する。

本体バグとして再現できるものは、unit / Cypress regression に落として required CI へ入れる。再現できないが頻度が高いものは、次の PR で Sentry context や UI error 表示を改善する対象にする。

## full Cypress に何が残っているか

full Cypress の残りは主に `cypress/e2e/movidea/` の 23 specs である。初期確認では emulator なしの Movidea 単独実行で 17 specs failed / 7 tests pass / 18 tests failed だった。その後 Java 21 と Firebase emulator を用意して実行し直すと、23 specs / 25 tests のうち 9 tests pass / 16 tests fail、Cypress summary では 15 of 23 specs failed だった。

主な failure 系統:

- 旧 DOM class / text / button 前提
- pixel exact な座標期待値
- Cypress actionability と `pointer-events: none` の衝突
- hidden MUI menu や covered element への古い操作前提
- Firebase emulator を前提にする login / save
- `visit_reset` など旧 API / 旧 global state 前提

つまり、Movidea legacy は「通すべきテスト」と即断しない。歴史的 regression として価値があるケースを棚卸しし、現行 Kozaneba で守りたい挙動だけを unit/integration test または Kozaneba spec に昇格させる。古い UI 形状に依存するだけの spec は quarantine または削除候補にする。実測に基づく spec 別の分類は [Movidea legacy test inventory 2026-06](../sources/movidea-legacy-test-inventory-2026-06.md) に分けて保存した。

CI でまったく動かさないのではなく、当面は non-required / scheduled / quarantine として観測し、artifact と失敗件数を残すのがよい。merge を止める gate にはしない。

## Cypress helper 整理の位置づけ

Cypress helper 整理は有効だが、順番としては「残す spec を分類した後」でよい。

先に helper を全面整理すると、古い Movidea UI 前提を延命する作業と、Kozaneba 本体で必要な状態検査 helper を作る作業が混ざる。まず required CI に載せる Kozaneba 本体側を安定させ、その後に残す legacy spec を選んでから helper を整理する。

整理するなら次を優先する。

- `hasPosition` の完全一致を、許容誤差付き DOM assertion または state assertion に分ける。
- drag helper は DOM element への direct trigger と、実ユーザー操作に近い canvas 起点 mouse sequence を分ける。
- `cy.getGlobal()` / `cy.setGlobal()` / `cy.updateGlobal()` を、明示的な test API として育てるか決める。
- emulator 起動、login、save、reset を共通 helper に寄せる。

## Playwright は今は入れない

Cypress だけで必要な確認ができるなら、Playwright を足して複雑にしない方がよい。

Playwright を検討する条件は、具体的な Cypress の不足が見えたときに限る。たとえば、IME、多タブ、pointer capture、ブラウザ間差分、DPR 周りで Cypress では信頼できない failure が出る場合である。

現時点の優先順位は、Cypress か Playwright かの比較ではなく、状態モデルと座標ロジックのテストを厚くし、Kozaneba 本体の Cypress gate を required にすること。

## 3. CI gate が安定したら Node / CRA 脱出

Node 更新と CRA / `react-scripts` 脱出は、required CI が安定してから行う。

移行前に満たしたい条件:

- 座標ロジックの単体・統合テストが入り、nested drag 型の regression を CI で検出できる。
- `npm test -- --watchAll=false`、`npm run build`、`npm run codex:preflight`、`npm run cypress:emulator-smoke` が required CI で安定している。
- Kozaneba 本体 Cypress 17 specs / 31 tests が required CI で安定している。
- Movidea legacy は required ではなく、分類方針が決まっている。

この状態になってから、Node version 更新、`firebase-tools` / dependency 整合、CRA から Vite 等への migration spike を clean worktree で行う。CI gate が安定していれば、移行時の failure が「migration のせい」なのか「もともとの不安定 test」なのかを切り分けやすい。

## 2026-06-03 実施結果

上の 3 段階は実施済みになった。

- PR [#40](https://github.com/nishio/kozaneba/pull/40): nested drag 修正の知見を座標ロジック単体テストへ移した。
- PR [#41](https://github.com/nishio/kozaneba/pull/41): `Unit, build, and preflight` と `Cypress with Firebase emulator` を GitHub required CI にした。
- PR [#42](https://github.com/nishio/kozaneba/pull/42): Node 24 を `.nvmrc`、CI、Netlify に反映した。
- PR [#43](https://github.com/nishio/kozaneba/pull/43): CRA / `react-scripts` から Vite / Vitest へ移行した。
- PR [#44](https://github.com/nishio/kozaneba/pull/44): Vite の `import.meta.env`、Node 24 types、timer 型の後処理をした。

`work/kozaneba` の main は `d5757f5` で、post-merge の Kozaneba CI は success。Dependabot open alert も 0 件になった。

その後、#13「CI/CD パイプラインの構築」は完了コメント付きで close し、#4「本番環境のコンソールログ削除」は PR #45 で runtime `console.log` / `console.time` / `console.timeEnd` を dev-only logger に寄せて close した。

したがって、このページの「Node / CRA 脱出前に満たしたい条件」は満たされ、移行も完了した。今後のテスト改善は、#17「テストカバレッジの向上」を広いまま扱わず、座標変換、hit test、undo/redo、保存復元、Sentry 上位 error の regression などへ分解して進める。

## #17 の分解と Movidea legacy 棚卸し

#17 は「テストカバレッジを上げる」という広い作業名のまま進めない。次の小さな regression 単位へ分け、各単位ごとに「既存 Movidea test から救うのか」「Kozaneba test に書き直すのか」「新規 unit/integration test として作るのか」を決める。

- 座標変換: world / screen 変換、zoom、parent chain offset、root / nested 間 drag。
- hit test: pan / zoom 後の selection、group / kozane / line label の当たり判定。
- undo / redo: 今回の quick grep では旧 Movidea spec から直接の手がかりは見つからないため、現行仕様または今後の実装単位から新規 regression として切る。
- 保存復元: Firebase emulator、localStorage fallback、import JSON、`#edit=<id>` 復元、読み取り専用 / 書き込み可能状態。
- production error regression: Sentry 上位 error のうち本体バグとして再現できるもの。

この分解と並行して、旧 Movidea の Cypress test を棚卸しする。`cypress/e2e/movidea/` は 23 specs / 1452 lines あり、全部を直して required gate に入れる対象ではないが、歴史的 regression の種としては価値がある。

2026-06-03 に Java 21 + Firebase emulator で現行コード上の実挙動を確認し、旧 Movidea specs を spec 単位で分類した。詳細は [Movidea legacy test inventory 2026-06](../sources/movidea-legacy-test-inventory-2026-06.md)。

結果の要約:

- promote: 13 specs。座標、group 内外 drag、selection hit test、import/save/auth など、現行 Kozaneba の unit / integration / Cypress に移す。
- rewrite-before-decision: 5 specs。旧 helper や旧 menu 操作では判断できないため、現行 UI/API で再現してから残す範囲を決める。
- delete: 5 specs。空 test、旧 API 検査、旧 state 形状だけの test、既存 Kozaneba test と重複する tutorial など。

主なコード上の理由:

- `window.movidea` は残っているが、現行 state は `itemStore` / `drawOrder` 中心であり、旧 `kozane` / `fusens` 配列は存在しない。
- `hasPosition` は `getBoundingClientRect().x/y` の完全一致なので、1px 差や layout 差が product regression と混ざる。
- 現行 drag は `fast_drag_manager` が対象要素を一時的に `pointer-events: none` にするため、旧 direct trigger と衝突する。
- `ItemCanvas` は `drawOrder`、`selected_items`、`is_selected` を購読するため、`itemStore` だけを直接 mutate する旧 test は redraw 契約を満たさないことがある。

棚卸しの分類:

| 分類 | 主な spec | 扱い |
| --- | --- | --- |
| 座標 / drag / group | `dimension.cy.ts`, `transform.cy.ts`, `drag*.cy.ts`, `group_translated.cy.ts`, `nested_group.cy.ts`, `scaled_fusen_group.cy.ts` | pixel exact DOM assertion をそのまま直すのではなく、state invariant / world 座標の unit・integration test に昇格する候補を抜く |
| selection / hit test | `selection.cy.ts`, `three_fusens.cy.ts` | `selected_items` や selection rectangle の state assertion に寄せ、現行 `kozaneba/test_selection.cy.ts` と統合できるか見る |
| dialog / layout / tutorial | `add_kozane_dialog.cy.ts`, `adjust_font_size.cy.ts`, `scaled_fusen.cy.ts`, `tutorial.cy.ts` | UI 文言や CSS pixel 前提は削り、追加 dialog と tutorial の主要契約だけ Kozaneba spec に残す |
| import / save / restore / auth | `import_json.cy.ts`, `group_regroup_json.cy.ts`, `visit_reset.cy.ts`, `login.cy.ts`, `save.cy.ts`, `tutorial.cy.ts` | Firebase emulator smoke と保存復元 regression に統合する。旧 API 前提だけなら quarantine または削除 |
| 価値が薄い・コメント化済み | `group.cy.ts`, `many_fusen.cy.ts` | 固有の regression が残っていなければ、理由を残して削除候補にする |

各 Movidea spec には、最終的に次のどれかのラベルを付ける。

- **promote**: 現行 Kozaneba の必須挙動として unit / integration / Kozaneba Cypress に移す。
- **keep-quarantined**: 歴史的価値はあるが required gate にはしない。scheduled / non-required で失敗件数だけ観測する。
- **delete**: 古い DOM 形状、旧文言、空 test、重複 test だけで、守るべき挙動が残っていない。
- **rewrite-before-decision**: helper や emulator 整備がないと価値判断できない。

この棚卸しが済むまで、Movidea legacy helper を全面整理しない。先に helper を直すと、削除すべき古い UI 前提を温存する作業になりやすい。

## 成功条件

- nested group の root / nested / nested 間移動で、world 座標と親子関係の regression が unit/integration test で落ちる。
- Kozaneba 本体の required CI が、boot、build、save smoke、tutorial、drag regression の破壊を検出する。
- Movidea legacy は「残す価値のある挙動」と「古い UI 前提」を分類済みになる。
- Node / CRA 脱出に着手するとき、壊れた箇所を CI の差分として説明できる。
