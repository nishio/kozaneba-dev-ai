## このテーマの問い

[Kozaneba](../entities/Kozaneba.md) の長期的な重心が「**[こざね](../concepts/こざね.md)(情報の断片)中心**」から「**断片の間の関係中心**」へ移動しているのではないか、という仮説の検証。

## 仮説

2026-05-16 のセッションで nishio:

> こざねの形で表現されている断片自体よりも、その関係性を上手く扱いたい。紙の時代には線を引くこと自体が大変だったので断片の側にエフォートが偏ってしまっていた。

つまり「断片に重きを置いた設計」は **紙の物理的制約に由来する歴史的バイアス** であり、デジタル化の本来の機会はそこではなく「関係性の操作」にあったのではないか。

## 紙時代の物理的制約

紙の KJ法 / [こざね法](../concepts/こざね法.md) では:

- 線を引くにはペンが要る、消しゴムでは消えない、配置を変えると引き直し
- 必然的に「線を引く前に配置を完璧に決める」(KJ法では空間配置完了後に線を引いていた、[線を引く機能](../concepts/線を引く機能.md))
- [こざね法](../concepts/こざね法.md)(梅棹)に至っては線を引かず、紙の断片を物理的に綴じる
- 結果として **断片(=こざね)** が主役、関係は副次的

## デジタル化の段階的気づき

### 第 1 段階(〜2021): 紙の電子化

- [grouping → Regroup → Movidea → Kozaneba](系譜.md) の系譜は「紙の不便を電子化」が動機
- 「動かしながら整理する」=断片の操作が主、関係は配置で表現

### 第 2 段階(2021-12〜): 線の重要性が見えてくる

[Kozaneba:体験過程と意味の創造](../../raw/scrapbox_kozaneba/2021-12-08__Kozaneba_体験過程と意味の創造.md):

> 線がなければ付箋は近接という関係しか持てない。付箋は一つの場所しか持てないので、明確な境界はないとは言え階層的分類の要素が出てくる。

[線を引く機能](../concepts/線を引く機能.md) が「必要不可欠」と判定される。ただしこの段階の線は「関係の存在を示す」のみ。

### 第 3 段階(2025〜): 関係の中身が必要になる

- 概念マップ用途で [辺ラベル](../concepts/辺ラベル.md) が欲しいと気づく
- [いどばた/Keichobot→概念マップ→Kozaneba/Miro](../../raw/scrapbox_kozaneba/2025-11-14__いどばた_Keichobot→概念マップ→Kozaneba_Miro.md): [Keichobot](../entities/Keichobot.md) 的コーチングは「概念とその関係」を抽出する。Kozaneba に辺ラベルが無いのが現ニーズに不足
- [広聴AI](../concepts/広聴AI.md) のリーフノードを付箋として配置するアイデアでも、点ではなく **空間配置(=暗黙の関係構造)** が中核

### 第 4 段階(2025-08-29 の言明): 断片偏重への自覚

> 紙の時代には線を引くこと自体が大変だったので断片の側にエフォートが偏ってしまっていた

これは「断片中心の設計」が **意図ではなく制約由来のバイアス** だったと nishio 本人が言語化した瞬間。

## 名前(Kozaneba)に残る痕跡

プロダクト名 [Kozaneba](../entities/Kozaneba.md) = 「こざね(断片)を置く場」。名前自体が断片中心の世界観を埋め込んでいる。重心が関係に移るなら、名前と齟齬が出てくる可能性がある。

cf. [系譜](系譜.md): `grouping → Regroup → Movidea → Kozaneba` という改名の歴史を考えると、重心移動に合わせた改名も選択肢になりうる。

## [2つのKozaneba](Canvas移行の検討.md#2つのKozaneba) 議論との接続

[Canvas移行の検討](Canvas移行の検討.md) で nishio は:

> 10000 件以上のものをどうするかという路線と、1000 件未満の付箋を作りながら構造化していく Kozaneba は無闇に同一視しない方が良い

両者を「断片中心 vs 関係中心」の軸で見直すと:

| | 規模 | 重心 |
|---|---|---|
| 既存 Kozaneba | 〜1000枚 | 断片中心(KJ法 / こざね法のデジタル化) |
| Canvas プロト(広聴AI 系) | 10000+ | 関係中心 / 構造可視化(UMAP配置・密度可視化) |
| 概念マップ用途 | 中規模 | **関係中心** ←ここが新しい |

つまり「2つの Kozaneba」は規模だけで分けるのではなく、「断片中心」「関係中心」という重心の違いでも分かれる可能性がある。**概念マップ用途は規模では既存 Kozaneba 側だが、重心では Canvas プロト側に近い**。

## 設計判断への含意

「関係中心」を新しい設計の中心軸に据えるなら:

1. **線(エッジ)を一級市民にする**: 単なる「描画要素」ではなく、ラベルとイベントリスナを持つオブジェクト([辺ラベル](../concepts/辺ラベル.md))
2. **「先回りした N項関係」ではなく、用途別の関係種別**: 1:1、1:N(同性質グループ)、(始点, 関係種別, 終点)の三項関係(cf. [活用されなかった機能](活用されなかった機能.md))
3. **「囲んで畳む」より「ズーム/縮尺で見せる」**: 断片を物理的に束ねるのではなく、関係構造を視点で切り替える([なめらかな畳まれ](../concepts/なめらかな畳まれ.md))
4. **既存断片メタファーからの距離**: 「こざね」「付箋」という比喩は便利だが、関係中心の世界観では「ノード(節点)」「エッジ(辺)」というグラフ語彙の方が素直かもしれない

## 「ノード本文の関係負債」(2026-05 のソースから)

[raw/a.txt](../../raw/a.txt) で展開された GPT との議論で、この重心移動を支える有用なメタファーが提示された:**ノード本文に押し込まれているが、本来は関係オブジェクトの属性であるべき情報**を「関係負債」と呼ぶ。

```
Node A 本文:
  A は B と似ている。ただし B は認知の話で、A は制度の話。
  C を媒介にすると対応が見える。D では逆になる。
```

この文の大部分は、A の本文に置かれているが、実際は A-B 関係の属性として置くべきもの:

```
Relation Field:
  formulation: C を媒介に A-B が対応する
  participants: A, B, C, D
  aspects: 類似, 差異, 媒介, 反転
  modality: 仮説
```

つまり「断片中心の世界観」は、構造的に「関係的情報をノード本文に詰め込む」習慣を生んでいた。これを設計レベルで剥がすには、関係を第一級オブジェクトにし、[関係場](../concepts/関係場.md) として保持する必要がある(cf. [関係を第一級にする](関係を第一級にする.md))。

## 既存系譜との接続(2026-05)

ノード偏重批判は Kozaneba 固有の発見ではなく、Open Hypermedia、Wikidata の qualifier/reference、RDF 1.2 triple term、W3C N-ary Relations、IBIS / gIBIS、Unfolding Edges、ハイパーグラフ DB 研究などで繰り返し出てきた問題。詳細は [関係を第一級にする](関係を第一級にする.md) の「既存系譜」セクション。

ただしどれも「日常的な知的作業 UI としての実装」には至っていない。Kozaneba が探索している領域はそこ。

## 開いた問い

- これは「Kozaneba の自然な進化」か、「Kozaneba ではない別物への分岐」か?
- 関係中心に振った場合、KJ法 / [こざね法](../concepts/こざね法.md) との接続はどう保たれるか? それともそこは切り離すべきか?
