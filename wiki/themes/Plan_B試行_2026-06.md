## 仮説の前史(2025-08 サイド実験での体感)

本仮説は突然湧いたものではなく、2025-08-26~27 の Canvas プロトタイプ実装([pKozaneba2025-08-26~27](../../raw/scrapbox_kozaneba/2025-08-26__pKozaneba2025-08-26~27.md)、**本流ではなく [広聴AI](../concepts/広聴AI.md) 関連のサイド実験**)で nishio が次のように記録した体感が出発点:

> かつて僕が Kozaneba で実現した機能を GPT-5 は一発で出してくる… 僕の実装は英単語でも容赦なく改行するからこっちの方が優れてるかも。しかもデモンストレーション用のこのサンプルデータ自体を作ってんだよな。肌色変更絵文字とか超長い 1 単語とかのトラップに気づいてる。句点の禁則処理は入ってないけど「やれ」っていうだけでできそう。

つまり当時感じたのは:

- 過去に nishio 自身が時間を投じた実装(英単語改行・文字種別トラップ・禁則処理)を AI が **一発で出す**
- サンプルデータの生成まで自発的に整える
- 不足部分も「やれ」と言えば直る感触

これは「**賢い AI Agent は過去実装の悪いところを簡単に直す**」という本ページの仮説に近いが、対象がサイド実験のゼロからのコード生成だった点に注意:**本流の既存コードベースに局所的に手を入れる** という Plan B の状況は、ゼロから書く状況より難しい可能性がある。本実験はその差を測ることでもある。

### 2026-06-03 追加: 当のサイド実験の続きで見えた「AI が肩代わりしない判断」

このサイド実験は数日続き、2025-08-29 の commit を最後に停止している([pKozaneba2025-08-29](../../raw/scrapbox_kozaneba/2025-08-29__pKozaneba2025-08-29.md))。停止時点で nishio が悩んでいた問いは:

- クラスタ抽出方針:連結成分 vs 10 マス割り(どちらも欠点)
- マージ閾値:3 割 / 2 割 で実験、連鎖マージが起きる
- 路線統合判断:10000 件路線と 1000 件路線を同一視すべきか

これらは **AI ペアプロで肩代わりされなかった判断** であり、「AI が一発で出してくる」体験は **実装スピード** の話で、**設計判断のボトルネック** は別個に残ったまま停止していた。

つまり本仮説の正確な形は:

- ✅ **「賢い AI Agent は過去実装の悪いところを実装上は簡単に直す」**
- ❓ ただし **設計判断は AI が肩代わりしない**。むしろ AI が実装を高速化すると設計判断のボトルネックが顕在化する
- → Plan B 試行(辺ラベル UI 改修)では「実装スピード」と「設計判断のスピード」の両方を測る価値がある

**仮説**: 賢い AI Agent は、現 Kozaneba コードの「悪いところ」を簡単に直す。

## 渡す仕様(AI Agent 向け)

### 現状

- `work/kozaneba/` の main(コミット 5de81c2 時点)に対する作業
- `src/Global/TAnnotation.ts` の `RTLineAnnot` には既に `label: String.optional()` が存在
- 表示側は [Line.tsx](../../work/kozaneba/src/Canvas/Annotation/Line.tsx) で実装済み(ラベルがあれば中点付近に出る既定実装あり)
- **入力 UI が無い** — 既存の line に対してラベルを後付けする動線が存在しない

### 達成したいこと

ユーザが「線にラベルをつける / 編集する / 消す」を、**思考の流れを止めずに** できるようにする。

### 必須要件

1. **既存の線にラベルを後付けできる**
   - 線をダブルクリック(または同等の意図的操作)で編集 UI が開く
   - 編集 UI は inline(線の上の文字を直接編集する形)が望ましい。modal dialog は避ける
2. **既存データとの後方互換**
   - `label` フィールドが無い既存 line annotation がすべて動き続ける
3. **空ラベル = ラベル無し**
   - 編集 UI で全削除すれば「ラベル無し」状態に戻る(`label: undefined` または空文字列)
4. **線描画モード中(`line_start` != null)はラベル編集 UI を開かない**
   - 線を引いている最中のクリックはこれまで通り「線の終端確定」に使う

### やってはいけないこと(アンチパターン)

- **描いた瞬間に modal dialog を出さない** — 2025-09 Devin 実装の不採用理由([辺ラベル#エッジラベルダイアログが「ウザい」問題への別解](../concepts/辺ラベル.md))。これを再度踏まない
- **線を引いた瞬間に必須入力にしない** — 同上
- **ラベル機能のためにスキーマを破壊しない** — 既存 `label: String.optional()` を使う

### 推奨パターン(任意、優先度順)

1. **後から double-click**(Miro / tldraw / Obsidian Canvas 型)— [線UIサーベイ_2026](線UIサーベイ_2026.md) 参照。最も安全
2. **描いた瞬間 inline caret**(Whimsical / FigJam 型)— 線を引いた直後、中点に薄い caret が出て、書けば書く、書かなければ消える。modal ではない
3. **Kinopio 型 `connection-type`** — `label` を「型」として育てる方向は今回はスコープ外(将来拡張の余地は残す)

### 技術的な障害(既知)

- [AnnotationLayer.tsx](../../work/kozaneba/src/Canvas/Annotation/AnnotationLayer.tsx) は SVG レイヤ全体に `pointerEvents: "none"` を指定している
- 個別 `<line>` は `custom.is_clickable: true` のときだけ `pointerEvents: "auto"` に切り替わる
- 既存の line annotation は `is_clickable` がほぼ undefined = false 相当なのでクリックできない

→ **デフォルト挙動の変更が必要**。「常にクリック可」にすると物体ドラッグ中のヒット判定を線に取られて邪魔になる懸念があるので、設計判断ポイント(参照: [コード構造調査](../sources/kozaneba-code-architecture.md))。

代替案:
- (a) `is_clickable` のデフォルトを true に変える + マウス状態で挙動を切り替える
- (b) `pointerEvents` を編集モード時のみ有効化する
- (c) 線本体ではなく、線の中点に小さなヒットエリア(ボタン or invisible rect)を別途置く

どれを採用するかは AI Agent の判断に任せる。判断理由を PR 説明に書くこと。

### 成功条件

- [ ] 既存 line を double-click(または同等)してラベルを編集できる
- [ ] 編集後に画面に反映される
- [ ] リロードしても保存されている(Firestore)
- [ ] ラベル無しの線が引き続き動く
- [ ] 線描画モード中はラベル編集 UI が開かない
- [ ] 既存テスト(Jest / Cypress)が壊れていない
- [ ] modal dialog を新規導入していない

### 2026-06-02 白画面再発への追加対応

- nishio の再指摘:
  - `#blank` が完全に真っ白なら「空の場」ではなく UI boot 失敗であり、人間確認に戻す前に Agent 側で直すべき
- 原因候補:
  - `public/index.html` が Firebase UI CSS を gstatic から同期 stylesheet として読み込んでいた
  - `#blank` には不要な外部 CSS だが、通常ブラウザではこの外部リソース待ちが React bundle 実行前の白画面に見える可能性がある
- 修正:
  - 初期 HTML から `https://www.gstatic.com/firebasejs/ui/.../firebase-ui-auth.css` を削除
  - JS 起動前でも完全白画面にならないよう `#root` に最小の Kozaneba boot fallback を追加
  - Firebase UI CSS は `SignDialog` / `CloudSaveDialog` を開いた時だけ `ensureFirebaseUiCss()` で動的に読み込む
  - `authui.start(...)` を render 中実行から `useEffect` 実行に移動
- 追加テスト:
  - Cypress に `#blank` の HTML が gstatic Firebase UI CSS を含まないこと、boot fallback と bundle script を含むことを確認するテストを追加
- 検証:
  - `env -u ELECTRON_RUN_AS_NODE npx cypress run --spec cypress/e2e/kozaneba/test_line_label.cy.ts --config video=false`: pass (4 tests)
  - `npm test -- --watchAll=false`: pass
  - `npm run build`: pass
  - `www.gstatic.com` を遮断した headless Chrome screenshot でも `#blank` の AppBar / StatusBar 表示を確認

### 2026-06-02 通常 Chrome プロファイル固有の boot 失敗経路

- 見直し:
  - headless Chrome / Cypress は新規プロファイルで通るが、人間の通常 Chrome だけ白画面になるなら、通常プロファイルの保存状態を疑うべき
  - Kozaneba は起動時に `localStorage.onLoad` を `eval` しており、ここは通常 Chrome にだけ残る
- 原因候補:
  - 保存済み `onLoad` ユーザースクリプトが古い API や不正な状態を参照して例外を投げると、React mount 前に boot が止まり完全白画面になる
- 修正:
  - `run_user_script()` を `try/catch` で保護し、ユーザースクリプト失敗時もアプリ本体の boot を止めない
  - Cypress に `localStorage.onLoad` が例外を投げても `#blank` の AppBar / canvas が表示されるテストを追加
- 検証:
  - `env -u ELECTRON_RUN_AS_NODE npx cypress run --spec cypress/e2e/kozaneba/test_line_label.cy.ts --config video=false`: pass (5 tests)
  - `npm test -- --watchAll=false`: pass
  - `npm run build`: pass

### 2026-06-02 Codex 実装前 preflight の追加

- 結論:
  - 機能実装前に、Codex が実装できる環境かを検査するゲートが必要
  - 手作業で「Cypress はこの環境変数を外す」「`#blank` は UI が出るべき」などを思い出す運用では不十分
- `work/kozaneba` で追加:
  - `scripts/codex-preflight.sh`
  - `package.json` の `npm run codex:preflight`
- preflight の確認内容:
  - Node/npm version と `ELECTRON_RUN_AS_NODE` の検出
  - dev server が `http://localhost:3000` で `#blank` を返すこと
  - 初期 HTML が boot fallback と bundle script を含み、gstatic Firebase UI CSS に依存しないこと
  - dev server の bundle が現在の実装(`onLoad` 失敗保護 / line label hit area)を含むこと
  - `env -u ELECTRON_RUN_AS_NODE` 付き Cypress
  - `npm test -- --watchAll=false`
  - `npm run build`
- 検証:
  - `npm run codex:preflight`: pass
- 含意:
  - 今後、Codex が Kozaneba 本体を触る前には `npm run codex:preflight` を先に通す

## 2026-06-03 人間体験での再評価 — 実装はノーオペだった

「Codex の実装は merge され、自動テストも通っているが、**人間が実ブラウザで触ると double-click が editor を開かない**」と nishio が指摘。コードを精査した結果:

- [AnnotationLayer.tsx](../../work/kozaneba/src/Canvas/Annotation/AnnotationLayer.tsx) の SVG root は CSS `pointerEvents: "none"` を持つ
- Codex の追加した hit area は SVG attribute `pointerEvents="stroke"` で hit を取りに行く
- 親 SVG element の **CSS `pointer-events: none` は子要素の SVG presentation attribute を上書きする**(現代ブラウザの一般的挙動)
- 結果: hit area は実ブラウザでイベントを受け取らない = **実装は事実上ノーオペ**
- Cypress テストが pass していたのは `cy.testid(...).dblclick({ force: true })` を使い、ブラウザの hit testing を完全バイパスして event handler を直接叩いていたため

つまり「コードは merge された、テストは pass した、でも機能は動かない」状態。**自動テストが機能正しさを保証していなかった**。

## 2026-06-03 ドラッグ不変条件と spec の不備

仮に上記を修正(hit area の指定を CSS に変える)すると、今度は別の問題が出る:

- hit area の幅は `hit_stroke_width = max(stroke_width + 12, 16) = 16px`
- これが clickable になると、線の上 16px 幅で **kozane drag 開始が妨害される**
- [release-notes-2021-2025](../sources/release-notes-2021-2025.md) に記録された 2021-09 の設計原則 `949a1fd: all lines are now non-clickable` を破る
- [活用されなかった機能](活用されなかった機能.md) の「default で線が増えない方を選ぶ」哲学とも逆行

本ページの当初 spec で「後から double-click(Miro / tldraw 型)— **最も安全**」と書いたのは私(spec writer LLM)の誤り:

- Miro/tldraw は「線を選択 = 主要操作」の世界観だが、Kozaneba は「線は装飾、kozane を動かすのが主要操作」
- 主要操作が違うので「最も安全」の判定は逆だった
- spec で「設計判断ポイントです」と丸投げした結果、Codex は drag 不変条件を意識せず 16px hit area を選んだ

→ **spec writer 側と AI Agent 側の二段の踏み外し**。この経験から、Codex に投げる前に spec で潰すべき項目があった。詳細は [AI委託の設計と検証 2026-06](AI委託の設計と検証_2026-06.md)。

## 仮説への最終判定

> **仮説**: 賢い AI Agent は過去の実装の悪いところを簡単に直す。

判定: **条件付き NO(当初の Codex 試行のみで言えば)**。

- コード改修自体は局所的に書けた
- だが **(1) 実ブラウザで動かない** + **(2) 仮に直しても設計原則を破る** ため、機能としては「直した」と言える状態ではなかった
- 「直る」のは:
  - spec が hard constraints を漏れなく書き、
  - 自動テストが実ブラウザ hit testing を含み、
  - 人間検証が完了宣言の前段にあるとき
- 上記が揃わない試行で測れたのは「**AI Agent のコード生成能力**」だけで、「**過去実装の悪いところを直す能力**」は測れていない

副産物(これは確かに直った):
- 白画面の boot 健全性問題(Firebase UI CSS / `localStorage.onLoad` の eval)
- preflight gate (`npm run codex:preflight`)
- これらは **辺ラベル UI 本体とは無関係に、過去先送りされていた負債**が AI Agent の作業を通じて掘り起こされたもの
