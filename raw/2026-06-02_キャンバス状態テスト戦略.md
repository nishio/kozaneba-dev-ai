# より良いテストについて相談した

基本方針は、「見た目のキャンバス」ではなく「キャンバス上の状態」を主にテストすることだと思います。
ピクセル単位のE2Eに寄せすぎると、フォント、アンチエイリアス、DPR、OS差分で壊れやすいです。

## 1. まず状態モデルを厚めにテストする

付箋アプリなら、中心はたぶんこういう状態です。

```ts
type BoardState = {
  notes: {
    id: string
    x: number
    y: number
    width: number
    height: number
    text: string
    zIndex: number
  }[]
  selection: string[]
  viewport: {
    scale: number
    offsetX: number
    offsetY: number
  }
}
```

ここに対して、UIを通さずにテストします。

たとえば：

```ts
moveNote(state, noteId, dx, dy)
resizeNote(state, noteId, edge, dx, dy)
selectNotesInRect(state, rect)
zoomAtPoint(state, screenPoint, nextScale)
panViewport(state, dx, dy)
undo(state)
redo(state)
```

この層で重点的に見るべきなのは、次のあたりです。

* 付箋を移動したら、対象の x/y だけが期待どおり変わる
* 複数選択して移動したら、全付箋が同じワールド座標差分で動く
* ズームしても、マウス位置の下にあるワールド座標がずれない
* pan / zoom 後でも hit test が正しく動く
* undo / redo が移動、編集、削除、複数選択操作に対して破綻しない
* grid snap があるなら、丸め誤差や負座標で壊れない
* z-index や重なり順が hit test に反映される

特にキャンバス系では、screen座標とworld座標の変換がバグの温床です。ここは単体テストを多めに書く価値があります。

```ts
expect(screenToWorld({ x: 200, y: 100 }, viewport)).toEqual(...)
expect(worldToScreen(worldPoint, viewport)).toEqual(...)
```

さらに、性質ベースのテストも相性がよいです。

```ts
worldToScreen(screenToWorld(p, viewport), viewport) ≒ p
```

のような性質をランダムな座標・倍率・オフセットで検査できます。

## 2. ドラッグ操作は「イベント列 → 状態変化」としてテストする

UIのドラッグを全部ブラウザE2Eで検証するより、まずは内部的にこういう関数へ落とせると安定します。

```ts
dragController.pointerDown(...)
dragController.pointerMove(...)
dragController.pointerUp(...)
```

そして、

```text
pointerDown on note A
pointerMove by 100px
pointerUp
```

の結果として、状態がどう変わったかを見る。

ここで重要なのは、最終的な描画ではなく状態を見ることです。

悪い寄せ方：

```ts
expect(canvasScreenshot).toMatchSnapshot()
```

主テストとしては壊れやすいです。

良い寄せ方：

```ts
expect(board.notes.find(n => n.id === "a")?.x).toBe(120)
expect(board.notes.find(n => n.id === "a")?.y).toBe(80)
```

## 3. PlaywrightなどのE2Eでは、少数の代表操作だけ確認する

E2Eでは、ブラウザ実装に依存する部分を確認します。

* pointer events
* pointer capture
* canvas の bounding box
* devicePixelRatio
* 入力欄やIME
* スクロール、リサイズ
* 保存・復元
* 実際のユーザー操作のつながり

Playwrightなら、キャンバスの位置を取ってマウス操作します。

```ts
const canvas = page.locator("canvas");
const box = await canvas.boundingBox();
await page.mouse.move(box!.x + 100, box!.y + 100);
await page.mouse.down();
await page.mouse.move(box!.x + 200, box!.y + 140);
await page.mouse.up();
const state = await page.evaluate(() => window.__TEST_API__.getBoardState());
expect(state.notes.find(n => n.id === "note-1").x).toBeCloseTo( /* expected */ );
```

このために、テスト環境だけで使えるAPIを生やしておくのは有効です。

```ts
window.__TEST_API__ = {
  getBoardState,
  setBoardState,
  flushAnimations,
}
```

公開APIではなく、テストビルド時だけ有効にする形でよいです。

## 4. E2Eで見るべき代表シナリオ

全部をE2Eにしない前提で、代表的にはこれくらいで十分だと思います。

付箋の基本操作

* 付箋を作る
* テキストを編集する
* 付箋をドラッグ移動する
* 付箋を削除する
* 保存してリロード後に残っている

キャンバス操作

* pan できる
* zoom できる
* zoom 後に付箋をドラッグできる
* pan 後に hit test がずれない
* ブラウザウィンドウをリサイズしても操作できる

複数選択

* 矩形選択
* Shift/Cmd追加選択
* 複数付箋の移動
* 選択解除

undo / redo

* 作成
* 移動
* 編集
* 削除
* 複数移動

入力まわり

* 日本語入力
* 改行
* 長文
* 空文字
* コピー＆ペースト
* ショートカットキー

保存・同期

* localStorage / IndexedDB / API保存
* リロード復元
* 保存失敗時の扱い
* 複数タブやリアルタイム共同編集があるなら競合処理

## 5. visual regression は薄く使う

スクリーンショット比較は有用ですが、主役にしない方がよいです。

使うなら、次のような固定ケースに絞るのがよいです。

* 空のキャンバス
* 付箋が数枚ある状態
* 選択中の付箋
* 複数選択中
* zoom / pan 後の状態
* 日本語テキスト
* 長文テキスト
* 付箋が重なっている状態

また、差分が出やすいので、テスト環境を固定します。

* viewport size固定
* deviceScaleFactor固定
* フォント固定
* アニメーション無効化
* 時刻・乱数・ID生成を固定
* OS差分の影響を減らすためCI環境を固定

visual regression は「描画が明らかに壊れていないか」を見るためのもの、座標ロジックの正しさは状態テストで見る、という分担がよいです。

## 6. キャンバス系で特にバグりやすい箇所

ここは重点的にテストした方がよいです。

```text
screen coordinates
  ↓
canvas local coordinates
  ↓
world coordinates
  ↓
note coordinates
```

この変換経路で、以下が絡むと壊れやすいです。

* devicePixelRatio
* CSS transform
* canvas の CSS size と描画バッファ size の違い
* ページスクロール
* ブラウザズーム
* pan / zoom
* ウィンドウリサイズ
* pointer が canvas 外へ出たとき
* touch / trackpad / mouse の差
* 小数座標の丸め
* 負座標
* 非常に大きな座標
* 付箋の重なり

たとえば、こういうテストはかなり有効です。

```ts
test("zoomAtPoint keeps the world point under cursor stable", () => {
  const viewport = { scale: 1, offsetX: 100, offsetY: 50 };
  const cursor = { x: 300, y: 200 };
  const before = screenToWorld(cursor, viewport);
  const nextViewport = zoomAtPoint(viewport, cursor, 2);
  const after = screenToWorld(cursor, nextViewport);
  expect(after.x).toBeCloseTo(before.x);
  expect(after.y).toBeCloseTo(before.y);
});
```

## 7. テストしやすい設計にしておく

キャンバスUIは、設計次第でテストの難易度が大きく変わります。

おすすめは、次の分離です。

```text
pointer / keyboard events
        ↓
interaction controller
        ↓
commands
        ↓
state reducer
        ↓
renderer
```

つまり、イベントハンドラ内で直接 canvas に描画したり、DOM状態を書き換えたりしない。

```ts
dispatch({ type: "NOTE_MOVED", id, dx, dy })
```

のような command / action に落とすと、テストしやすくなります。

描画はあくまで、

```ts
render(canvas, boardState)
```

のように、状態から導出されるものにする。

この形にしておくと、

* reducer は単体テスト
* interaction はイベント列テスト
* renderer は少数のvisual regression
* E2Eは代表シナリオ

という分担ができます。

## 8. 実務的なテスト配分

自分ならこうします。

多め:

- 座標変換
- hit testing
- move / resize / select
- undo / redo
- persistenceの変換処理

中くらい:

- interaction controller
- pointer event sequence
- keyboard shortcut

少なめ:

- Playwright E2E
- screenshot regression

比率でいうと、E2Eよりも単体・統合テストを厚めにします。
キャンバスアプリのE2Eは価値がありますが、細かい座標まで全部見ると壊れやすくなります。

## 9. かなり大事な判断

「付箋がそこに見えているか」ではなく、「付箋のworld座標が正しいか」を基本の正解にする。

そのうえで、最低限のスクリーンショットテストで「状態が正しく描画されているか」を確認する。

この分担が一番安定すると思います。
